## 1. 交付结果与边界

首交付 M1：用户只打开 MuSpace，在一个实际项目工作区内导入真实研究成果与论文，阅读并记录页码/引句笔记，创建任务并导出，在外部设备执行后返回结果，人工判断接纳，关联到提纲并导出报告；退出重开后资料、决定和关联仍在。macOS 与 Android 均实际跑通，允许手工选择传递渠道。一个完整真实科研链条优先于新全文索引、精确锚点、ResearchCase、研究卡、问答、OCR。

M2：补齐科研现有所有流程的迁入与回归；M1 不可宣称全量科研迁移完成。M3：完整询价模块用相同注册和存储机制迁入，验证平台没有科研专用假设。M4：阅读检索/问答等新能力及原型接入。Windows 构建兼容验证后续完成，M1 不声称 Windows 已验收。总体产品仍以个人 Agent 为核心；本期通过共用领域接口为 Agent 留出实际调用通道，无模型不影响科研链条。

MuSpace 是唯一安装和入口。静态 Flutter 业务模块随主应用构建；不保留旧应用独立发布要求，不建设动态下载代码市场。没有旧用户数据，代码和包格式需迁入，旧安装数据库无需转换；首次发布以后的升级仍须可验证。

## 3. RALPLAN-DR

原则：①完整业务闭环先交付；②平台管资源，模块管业务含义；③单一事实来源；④复用当前可工作的实现；⑤验证证据分级。

三个驱动：迁入后保留实际业务；一个应用内可扩展到第二模块；离线与可恢复存储。

| 选项 | 优点 | 代价/适用边界 | 决策 |
|---|---|---|---|
| A 同仓静态业务包，保留领域实现，宿主集中资源和组装 | 能直接迁入完整页面及流程；领域维护边界清晰 | 需要拆开原 main/store 自管理职责，先完成作用域测试 | 选择 |
| B 先在单 Flutter app 内以目录划分业务，之后提包 | 初期路径和构建配置少，单模块启动快 | 第二模块更容易绕过边界，提包工作延后 | 可行但当前已有多业务资产，选择 A 降低后续返工 |
| C 先统一领域模型并重写全部科研页面 | 长期风格一致、模型一次整理 | 闭环交付慢，包兼容与业务丢失风险高 | 当前不选，收益不足以抵消迁入成本 |

平台不承诺恶意同进程 Dart 代码沙箱；模块分库是所有权和维护边界。

研究领域接口留在 research_module，不放进公共 API；共享 API 不依赖科研或询价。依赖方向 app → module/api，module → api；业务模块不互相访问实现。App 组合根显式列出 `ResearchModule()`，后续加 InquiryModule。宿主只有一个 MaterialApp/router，模块提供可挂载业务页面和子路由。不为了形式给每个小功能拆包，不强制把现有状态管理重写为新模式。仅迁入已用依赖；新路由或状态库选择需按实际 SDK 兼容核定，不能让某框架成为闭环前置。

源码采用同仓受控迁入：记录来源提交、许可证、原路径与目标路径，将科研代码复制提取为可维护模块后仅以 MuSpace 副本为本产品实现。不会在运行时从兄弟仓私有 lib 导入，也不要求兄弟仓先发布 D0。迁入改动在 MuSpace，兄弟仓保持证据源，未来上游修复按差异评估引入。

## 5. 模块契约与启动

最小伪接口（设计示意，不是可直接编译代码）：

```dart
abstract interface class BusinessModule {
  ModuleManifest get manifest; // id/apiVersion/requiredDependencies
  ModuleSchema get schema;    // version, definitionDigest, migrations
  List<ModuleRoute> get routes;
  Future<ModuleRuntime> activate(ModuleResources resources);
}
class ModuleResources {
  final ManagedDatabase database; // 宿主已完成升级，模块不自行 open/migrate/close
  final ModuleFiles files;         // 宿主授予的模块私有根及选取/导出能力
}
abstract interface class ModuleRuntime {
  Future<PreparedImport> prepareImport(SelectedInput input, ImportTarget target);
  Future<ImportReceipt> commitImport(PreparedImport input, ImportIntent intent);
  Future<ModuleSession> openSession(WorkspaceBinding binding);
}
abstract interface class ModuleSession {
  Future<ObjectView?> resolve(ObjectRef ref);
  Future<void> flush();
  Future<void> dispose(); // 释放会话资源，不关闭宿主持有的连接
}
class WorkspaceBinding {
  final String workspaceId, moduleId, nativeProjectId;
}
class ObjectRef {
  final String moduleId, objectType, objectId;
  final String? nativeProjectId, revisionRef;
}
```

生命周期：主库可用 → 注册静态模块并验证重复 ID/必要依赖/循环 → 注册导航和对象 opener → 用户进入模块时 StorageManager 获取唯一连接并执行 schema → 创建不要求项目绑定的 ModuleRuntime → 已绑定则 openSession 挂载业务页面，未绑定则挂载 runtime 的导入/创建入口。首次导入成功激活绑定后再创建 session。缺可选能力不阻断模块；缺必要依赖、库高版本或升级失败显示该模块不可用，不挂载半初始化页面。单一模块故障不阻断平台设置和其他健康模块。

模块状态 registered/opening/ready/failed；所有 open 请求去重，重试必须等待前次结束。页面切换不关闭 DB；工作区切换释放页面/session 订阅，已开始任务保留原 workspace/binding 快照并在原作用域提交。晚到结果不更新新工作区页面。应用退出先停止接收新操作、等待短写事务结束、flush，然后由 StorageManager 唯一关闭。移动系统强杀由事务与启动对账处理，不依赖 dispose 一定执行。

路由 `/workspaces/:workspaceId/research/:section`；对象打开解析 workspace/binding 后在模块内核对所属项目和对象是否存在。无绑定显示“导入研究或创建项目”；绑定缺失/失效显示修复入口，**绝不自动选择第一个项目**。模块内不再维护第二套全局项目选择器；跨工作区跳转必须先显式切换工作区。科研六个 section 名保持现有含义。

## 6. 数据与文件所有权

应用私有根由宿主唯一确定：`data/muspace.sqlite`；`data/modules/research/research.sqlite`；`data/modules/research/files/`。每业务模块一库，库内多个项目；不按每个 workspace 复制科研库。后续 inquiry/prototype 同级。主库拥有 workspaces、workspace_module_bindings、module_registry、schema_catalog、object_catalog；业务库拥有全部领域事实、schema_migrations、必要的 projection_changes。主库保存目标 schema 定义摘要/版本/完整声明清单及观察到的实际版本，不作为每次查询的动态表生成器。

绑定唯一键 `(workspaceId,moduleId)`，同时约束 `(moduleId,nativeProjectId)` 唯一，使一个科研项目只属于一个实际工作区。保留科研字符串原生 ID；workspace ID 与 project ID 不强行相等。若要未来一研究项目关联多个工作区，须独立改变唯一约束和可见性语义。

首次导入不依赖已绑定 session。runtime 的 `prepareImport(input, create(targetProjectId))` 或 `prepareImport(input, refresh(existingScope))` 在事务外冻结输入、校验/解析并生成 inputDigest 和 stagingToken；create 使用宿主预分配 ID，refresh 必须已存在且归属匹配。不能直接调用旧 `importResearch(intoProjectId)` 假装支持预分配新项目，该方法当前要求项目存在，必须拆改。

宿主随后在主库保存 ImportIntent：operationId 主键，workspaceId/moduleId/targetProjectId/importKind/inputDigest/stagingToken/status；待建绑定对 `(workspaceId,moduleId)` 限制单个活跃 create intent，重复点击复用同一 intent，禁止同时建立两个项目。commitImport 同步事务内再次核对目标、输入和已有回执，将创建项目（仅 create）、业务导入、ImportReceipt 和变更序列一起提交。失败回滚，不显示可见空项目。receipt 保存同一 operationId、workspaceId/moduleId/targetProjectId/importKind/inputDigest 及提交结果；同号同身份返回已有结果，同号异输入/目标/类型拒绝。重试沿用冻结输入，禁止重新读取可能已变化的外部路径沿用旧 operationId。

本库提交后宿主才激活 binding/完成 intent；激活前中断可根据本库 receipt 补齐。无 receipt 则用同冻结输入重试，暂存缺失明确要求新导入而不是报成功。refresh 直接使用已有 binding，不改项目归属、不按文件名猜项目。主库清理未完成 intent 前先核对本库回执，不能遗弃已提交项目。

最小治理表（具体 SQL 在任务1定义，业务语义保持模块内）：

| 库/表 | 关键字段与约束 | 对账依据 |
|---|---|---|
| 主库 module_registry | moduleId PK、apiVersion、packageRevision、status、lastError | 当前静态注册声明 |
| 主库 schema_catalog | moduleId PK、targetVersion、targetDefinitionJson、targetDigest、observedVersion、observedDigest、migrationStatus、checkedAt | 目标声明与业务库实际结构/迁移历史分别记录 |
| 主库 workspace_module_bindings | workspaceId/moduleId复合PK、nativeProjectId；moduleId/nativeProjectId唯一 | 已提交本库项目及ImportReceipt |
| 主库 import_intents | 上述operationId及身份、status；活跃create唯一约束 | 本库回执 |
| 本库 import_receipts | operationId PK、完整导入身份、resultJson、committedAt | 与业务数据同事务提交 |
| 本库 schema_migrations | version PK、migrationId唯一、definitionDigest、appliedAt | 已提交的版本化迁移 |
| 本库 projection_changes | seq递增PK、projectId、objectType/objectId、revisionRef、deleted | 与对应业务变更同事务 |
| 主库 projection_cursors | moduleId PK、lastAppliedSeq | catalog更新与游标推进同一个主库事务 |

启动把 schema_catalog 目标与模块声明比较，再以业务库 migration history 和实际 schema 验证 observed 字段；同版本不同 digest 属结构漂移，拒绝自动猜测修改并报告。业务库版本超前拒绝，主目录落后可重建；schema_catalog不能单独证明实际表正确。

建库/升级：模块声明版本化 migration；StorageManager 执行、单次事务内更新 schema_migrations/user_version，验证 foreign_keys/schema 后更新主库目录。业务库已提交但主库未更新时下次读取业务库历史修复目录；不以主库落后回滚已提交业务库。更高版本拒绝打开，失败保留当前数据库和错误，不自动清空重建。所有连接启用 foreign_keys；备份/恢复由宿主协调暂停模块写入，不能复制正在写的裸 sqlite 文件冒充一致备份。

旧 `WorkbenchStore.open(root)` 拆成模块声明 schema 与 `WorkbenchStore.attach(managedDatabase, moduleRoot)`。所有现有 store/exchange 查询写入保留在科研域；宿主不接管 notes/runs 的业务 SQL。每个物理库一个管理 owner，并统一经过轻量 `Future<T> write<T>(T Function(WriteContext) body)` 串行队列。body 内只做同步SQL，不含 await；异步文件复制/解析/hash/冻结在事务外prepare，排队后事务内重新读取项目/版本/回执等状态。旧 store/exchange 自行 BEGIN 的方法拆为外部 write 入口与无 BEGIN 的内部操作，禁止嵌套旧事务；业务、receipt、变更序列同事务提交。迁移和关闭也由同owner等待已排队短事务结束，关闭后拒绝新写；不能在长文件准备期间占用事务。查询可借领域服务做组合，禁止依赖跨 SQLite 外键或 WAL 跨文件原子提交。

文件由宿主提供私有根、选取、暂存、保存/分享及 hash/长度工具；research exchange 继续负责包 manifest、领域关系、版本、接纳语义和格式限制。模块持有附件记录及引用，平台不通过“通用导入器”改写科研字段。导入暂存校验后落盘，再领域登记；中断时可对账孤儿/缺文件，缺文件显式不可用，不能把记录存在当完整成功。首版不做跨模块 blob 去重，避免跨库引用计数成为前置。

对象目录为可重建摘要，不是第二套事实。业务事务同时递增变更序列/写 projection_changes，宿主幂等刷新主库 catalog 后记录消费位置；中断可重复消费，删除也传播。首次迁入可选择整项目重建目录作为恢复兜底。打开/导出/后续模型取材均回到领域服务确认可见性、存在和版本，不能凭过期 catalog 执行。

## 7. 业务接口与 Agent 接入

```dart
abstract interface class ResearchServices {
  // 首次create/再次refresh导入走上述ModuleRuntime prepare/commit契约。
  Future<ResearchDocument?> document(ResearchScope scope, String id);
  Future<void> saveNote(ResearchScope scope, NoteInput note);
  Future<ExportArtifact> exportTask(ResearchScope scope, TaskRef task);
  Future<ImportReceipt> importResult(ResearchScope scope, SelectedInput input);
  Future<void> assessRun(ResearchScope scope, RunRef run, Assessment input);
  Future<void> acceptRun(ResearchScope scope, RunRef run);
  Future<ExportArtifact> exportReport(ResearchScope scope);
}
```

Scope 来自宿主 session，服务每次核对对象属于该 project。以上入口映射现有 store/exchange；错误返回 invalid_input/not_found/scope_mismatch/unsupported_schema/integrity_failed/storage_full，并带可追踪操作号。完成状态、人工接纳、科学支持程度继续分开；页面和未来 Agent 工具调用同一服务。首交付只需证明一个只读对象查询和一个需明确动作确认的服务适配器与 UI 结果相同，真实模型和通用 Agent 引擎不作迁入门槛。科研每个按钮不必变工具。

### 外来任务与结果归属

任务包先prepare，读取原projectId/taskId/revision并保留，宿主决策后才commit：①包项目等于当前绑定，导入当前session；②已绑定其他工作区，明确提示并切到该工作区后导入；③包项目不存在且当前工作区无绑定，使用其原projectId建立intent，项目/任务/receipt同事务创建并绑定；④当前已绑定另一项目，为来件新建工作区并按③导入。包项目本库存在但绑定因中断缺失时先按intent/receipt恢复归属，不重复创建。相同任务/修订重复输入返回已有结果，身份相同内容不同报冲突，不改包ID以强行塞进当前项目。

结果按taskId + taskRevision定位已存在任务并取得其projectId，再核对scope/工作区；属于其他工作区则要求明确切换，未知任务/修订拒绝并提示先导入对应任务，不自动建任务、不只检查全库存在。晚到操作沿用发起时scope，不静默切当前页面。结果附件hash校验结果manifest；原任务身份/修订与先前任务导出相符，新日志无需与原任务输入附件hash相同。

## 9. 设计来源及适用边界

[Flutter 架构指南](https://docs.flutter.dev/app-architecture/guide)、[包与原生插件区别](https://docs.flutter.dev/packages-and-plugins/developing-packages)支持 UI/数据职责和模块提取，不要求重写全部为同一状态框架；[Now in Android 固定版本模块化说明](https://github.com/android/nowinandroid/blob/a49ed253d75e61a2b6ab80a8da677b57437b08eb/docs/ModularizationLearningJourney.md)借鉴 app 组装 feature/core，不把 Kotlin 示例当 Flutter 成熟度证明；[VSCode commands](https://code.visualstudio.com/api/extension-guides/command)与[Backstage 应用组装](https://backstage.io/docs/frontend-system/architecture/app/)借鉴注册和依赖注入，不引入插件市场或服务器。

[SQLite ATTACH](https://www.sqlite.org/lang_attach.html)、[外键](https://www.sqlite.org/foreignkeys.html)、[事务](https://www.sqlite.org/lang_transaction.html)限定分库一致性；[Drift migrations](https://drift.simonbinder.eu/migrations/)借鉴版本化结构与迁移测试，不要求把科研 sqlite3 立即改成 Drift。上述来源是已完成研究输入；方案为结合当前代码的工程判断，未声称作者或“顶级架构师”认可此具体方案。
