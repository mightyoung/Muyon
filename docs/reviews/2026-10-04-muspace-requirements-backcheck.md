# MuSpace 初始需求反查：迁入计划可用，产品与 V0.1 计划不完整

2026-10-04。依据用户本轮重述的九部分需求及此前明确决策，反查修订3的设计、PRD、实施计划和测试规范。只新增本报告，不修改已审查规划或历史共识，不执行产品代码。

## 1. 判断与责任

**当前计划可以作为科研迁入子计划，不能作为完整产品设计或完整 V0.1 发布计划。**

“首个交付是真实科研流程在 MuSpace 主体内跑通”确定了第一步，没有取消原 V0.1 的全文检索、选定论文问答、研究卡、研究包进出及 Windows 构建验证。上轮规划把“先迁入”扩大成“这些能力统归后续”，还让完整询价排在它们之前，这是规划范围的偏移，应纠正。

上轮 Architect → Critic 的 APPROVE 说明迁入路径的接口、事务和项目归属可实施；它没有充分检验总体需求是否保全。此次独立 Critic 反查结论是：**若用作完整产品/V0.1计划，REJECT；若用作迁入子计划，可保留。** 两个结论评价的范围不同，不改写历史审查记录。

仍保持已明确的后续决策：一个 MuSpace 安装入口、静态业务模块、工作区代表实际项目、没有旧用户数据库转换、主库＋业务分库且由 MuSpace 建库/升级。原需求“复用应用与数据”在此落实为业务实现、包格式、来源和资料保真，不重新增加旧安装数据库接入任务。

核验文件：[当前设计](../superpowers/specs/2026-10-03-muspace-v0.1-design.md)、[当前PRD](../superpowers/specs/2026-10-03-muspace-v0.1-prd.md)、[当前实施计划](../superpowers/plans/2026-10-03-muspace-v0.1-implementation.md)、[迁入验收规范](../superpowers/plans/2026-10-03-muspace-research-migration-test-spec.md)、[上轮共识及版本摘要](2026-10-03-muspace-migration-consensus.json)。以下行号对应此次核验的修订3。

## 2. 五处必须修正的问题

### 2.1 首个里程碑替代了整个 V0.1

证据：PRD:9–16把完整询价列为M3、FTS/卡/问答列为M4，Windows构建仅列“后续”；实施计划:47–49沿用该顺序。验收规范只有M1/M2停止条件，没有完整V0.1发布门槛。

**合理：** 迁入先交付，未实现的FTS/问答不能阻塞第一条真实流程。

**不合理：** 已明确属于V0.1的能力排到完整询价之后，并与OCR、记忆等版本外增强混成一项“新能力”。“原目标作为后续设计输入”不能替代发布任务与验收。

修正：保留迁入M1/M2，增加独立的V0.1完成里程碑。包含文字PDF与阅读批注、全文检索、选定论文问答、研究卡、研究包进出；macOS/Android实测，Windows构建验证。完整询价仍后置；验证平台通用性可先用一个小型测试模块，不需把完整询价当科研V0.1前置。

研究包进出必须单独验证。任务包和结果包往返，只覆盖执行交换，不能替代包含论文、研究卡和引用等内容的研究资料接续。

### 2.2 Agent 的核心定位没有落成产品路线

证据：PRD:5写“Agent以后调用”；设计:138–150只列科研服务及一读一写适配器。主/对象对话、工具发现、模型端点、权限策略、结果回页和助手执行记录没有对应实施任务。

**合理：** M1可不用真实模型，也不用先建设完整Agent引擎、Dream或生产级路由优化。

**遗漏：** “接口将来能被调用”不等于已有个人Agent设计。科研task/run属于业务事实；导入operationId/receipt属于提交记录；两者都不能代替助手执行任务的进展、运行设备、等待原因和产物记录。

修正分两层：

- M1主体确定最小扩展契约：对象/项目上下文引用、工具描述与参数、效应和权限、调用结果ObjectRef、执行记录关联。无需先实现完整Agent或通用调度系统。
- V0.1落实真实模型设置、选定论文取材、来源展示、对象上下文问答入口和结果回源。主对话/跨模块工具操作、持久任务管理另有具名阶段，不能永久写“以后”。

记忆先做有来源的偏好/背景/决定/经验及查看修改删除过期；后台整理/Dream另行增强且不扩权。工具选择器保持可替换，Jev/Laya只是评估候选，规则与大模型回退保留，不能无依据决定生产模型。

### 2.3 外层主体被缩成导航、数据库和科研容器

证据：设计:38–56的主体主要为bootstrap/router/workspace/storage/catalog；102–133集中数据治理。六个平台职责没有页面入口、数据所有者和阶段映射。FileGateway和对象目录覆盖部分公共机制，不是完整公共能力或知识中心。

修正：增加“职责 → 宿主服务 → 页面入口 → 数据所有者 → 交付阶段”的表。六个中心可以整合到少量页面，不要求六个导航项。

| 平台职责 | 最小承接方式 | 交付界限 |
|---|---|---|
| 工作台 | 项目、近期工作、任务和成果摘要，跳到业务对象 | M1至少有项目/近期科研入口；跨模块汇总随模块加入 |
| 消息中心 | 通知、待办、执行状态、通信消息，分别保留来源和对象跳转 | 初期承接实际已有事件；在线聊天加入时扩展，不把通知当执行回执 |
| 个人中心 | 单人资料、本人设备、偏好与记忆管理 | 设备/记忆阶段分别补齐，不强造账户服务器 |
| 数据与知识 | 文件/对象/引用查找、来源与关系跳转 | M1保留现有科研查找与跳转；V0.1全文检索/卡；跨模块关联随后补齐 |
| 接口与工具 | 统一登记模块、公共能力、第三方接口，参数/权限/调用与结果 | M1定登记契约；Agent操作阶段交付真实发现和调用管理 |
| 系统设置 | 模型、插件、存储、连接、外观、权限 | M1存储/模块基本状态；V0.1模型和外观；通信阶段连接与设备 |

公共实现归宿主创建和管理：文件/解析/预览/导出、搜索、模型、OCR、通信各有一个提供者，模块保留领域校验、取材、包格式和业务判断。M1不必实现所有服务；V0.1建设检索和模型时就采用公共机制，不能先在科研中造完整一套，询价中再造一套。

主库目录仍为派生摘要，不变成业务事实库。跨模块关系需有独立关联引用与来源职责，不能仅靠科研内部关系图宣称统一知识已完成。知识组织的可读文件目标也应有文件布局/索引/导出承接，不意味着嵌入Obsidian、GBrain或Palantir代码。

### 2.4 近期通信被手工传包替代了路线

证据：设计:168、实施计划:37/49仅保留LAN资产并统称后续；测试A3/A5证明人工渠道能完成科研链，没有设备可达性、链接、文字聊天、附件进度或确认的验收。

**合理：** M1跨网络经用户选择渠道传包；不建公网通信服务、群聊、离线服务器和自动全库同步。

**遗漏：** 用户明确的近期在线一对一通信仍需一条单独交付路线。不能从“不阻塞M1”推导为“不再计划”。

修正：在V0.1后给近期设备通信具名里程碑，明确连接条件及文件/链接/研究包发送、双方在线文字与附件、可达性/进度/接收确认/失败。无公网relay时如仅支持选定直连条件，明确写出边界；非同网研究任务仍由包交换保障。传输完成、导入成功、已读与人工接纳分别表示。

验收：两台本人设备实际传输；接收确认后才能显示已接收完成；中断不伪报成功；链接、文字、附件各有往返记录。无需由此扩张到群聊或复杂同步。

### 2.5 跨端体验没有完整承接

证据：设计:56/98主要给MaterialApp和科研路由；测试:31只有窄屏、大字号和六区入口。桌面并排、手机专页、浅深主题、阅读布局、减少动态缺乏任务和验收。

修正：M1确定宿主导航/内容区/对象入口，避免照搬旧桌面多标签页面。V0.1问答实现时交付桌面业务＋助手并排、手机上下文问答专页，保持项目/论文身份，回退不丢阅读状态。浅深主题和减少动态是主体体验，不与Dream/OCR一起无限延期。关系可视化先保证查找和跳转，不做大型图谱前置。

## 3. 九部分需求逐项保全表

“分期”必须有承接阶段、责任和验收；仅出现一个名词不算已经承接。下表阶段是本次纠偏建议，尚未修改原被审查计划。

| 初始要求 | 当前覆盖判断 | 应保留的阶段/责任 |
|---|---|---|
| 个人Agent核心，直接操作完整业务与助手两种入口 | 完整业务路线有，Agent产品路线缺 | M1完整科研；V0.1上下文问答；随后主对话/跨模块操作 |
| 跨端持续积累和接续 | 包往返有，平台任务/知识/设备承接弱 | 分别验收包接续、执行记录、跨模块关联、设备通信 |
| Flutter Android/macOS/Windows | 前两端M1清楚，Windows被无期限后置 | Windows构建在V0.1；M1早做跨端依赖检查以免迟发现阻断 |
| 离线阅读编辑检索管理，无云强依赖 | 迁入本地操作有，正文检索未进版本任务 | M1已有查找；V0.1离线全文检索；模型失效不阻断人工操作 |
| 本机/本人设备/自选远程模型，数据去向明确 | 无端点配置/调用计划 | V0.1显式profile与数据范围，无静默换端点；不可达明确失败 |
| 业务优先，基本原文件/引用/权限/传输完整性 | M1文件/hash/scope保护较明确 | 保留必要保护；选定资料取材和引用核验进入V0.1 |
| 复用现有业务与格式 | 迁入矩阵基本覆盖 | 保持现有页面、codec、任务/结果、关系与提纲，不造第二套规则 |
| 主对话、项目/对象专题，桌面并排手机专页 | 缺交付路径 | V0.1先对象问答；完整主/专题会话随后具名交付 |
| 工具发现/调用，UI与Agent同规则，结果回页 | 同领域服务原则有，登记/调用/权限缺 | M1最小契约；后续真实工具调用及ObjectRef回页 |
| 任务进展/设备/等待/产物/必要暂停取消恢复 | 只有科研任务及生命周期 | 单列助手执行记录；按操作能力支持控制，关聊天仍有状态 |
| 来源记忆、CRUD/过期与后台整理 | 只写“记忆增量” | V0.1后基础记忆阶段，再后台整理/Dream；不扩权 |
| 可替换选择器，Jev/Laya评估及回退 | 未承接 | 与Agent调用层解耦；生产模型未定，评估有任务而非预设采用 |
| 六个统一平台职责 | 缺映射 | 采用上节职责表，不必六个独立应用或导航 |
| research-workflow/skill手机阅读与论文全文 | M1有 | 保留真实来源与完整资料阅读证据 |
| 批注/摘录/精读及原文引用 | 当前页码引句能力有，精确范围未承接 | M1现有能力；V0.1引用可回源；精确定位增强不冒称已完成 |
| 论文/问题/方向/证据/实验/结论/卡关联 | 现有关系保留，新增卡/关系扩展笼统 | V0.1研究卡与来源关系；复杂研究过程增强随后明确任务 |
| 过程分支与决定原因，不强制阶段审批 | 有来源和run/评估，完整过程记录未承接 | 保留已有记录；演进能力具名后续，不强迫采用ResearchCase实现 |
| 研究/实验任务及资料跨网络导出执行 | M1基本有 | 人工选渠道有效；不强制同网或公网服务 |
| 执行状态/数据/日志/结论回导分析比较写作 | M1主链/M2比较有 | 原包身份与结果来源保真；回导状态不等于科学正确 |
| 研究包、任务结果、图、提纲不丢 | M1/M2较强 | 分别验收，不能用任务结果往返代替研究包完整交换 |
| 原文检索/限定资料问答/可信引用 | 被推M4 | 补回V0.1发布门槛 |
| 完整询价UI、供应商/报价/预算及Agent接口 | 有整模块迁入计划 | 完整迁入可V0.1后；不再先于明确的科研V0.1能力 |
| 原型组织展示后续搭建，受限Vue WebView小屏适配 | 有粗路线，搭建/桥接验收缺 | 保留V0.1后具名原型阶段；单页试点不等于完整MES |
| 新应用按统一注册进入 | 模块契约有，工具/公共服务契约不全 | 补登记与公共能力契约；小测试模块即可先验证通用性 |
| PaddleOCR、全文/向量/知识、模型、文件、交换通信各一套 | 文件较强，其余缺owner/阶段 | V0.1文件/正文检索/模型；OCR/向量/通信按独立阶段共用提供者 |
| 可读文件组织、跨领域可关联积累 | 私有文件根不等于此目标 | 定文件/对象索引及可读导出；后续跨领域关联，非产品代码嵌入 |
| 本人设备文件/链接/研究包、在线文字附件 | 人工包交换部分覆盖 | 近期设备通信单独阶段，全部子类型可验收 |
| 可达性、发送进度、接收确认、完成结果 | 缺 | 通信阶段实测，区分送达/导入/已读/接纳 |
| 无同网/公共云强制，复杂同步后置 | 人工跨网符合 | 保留包渠道；在线连接边界明确；群聊/离线服务器/全库同步后置 |
| Muse式独立业务＋上下文助手，浅深阅读/减动态 | 专业UI保留，主体交互欠缺 | M1宿主布局；V0.1并排/专页/主题/减动态验收 |
| V0.1科研、PDF、检索、问答、卡、研究包，Mac/Android与Win构建 | 未覆盖完整版本范围 | 必须恢复独立V0.1发布条件 |
| OCR/IM/向量/记忆Dream/Laya/询价/原型分期仍在总需求 | 名词在，无完整承接清单 | 有owner/阶段/依赖/验收的后续需求账本，不许因后置删除 |

科研链中的“人工接纳”是现有结果评价动作，可以保留；它不是新增“所有科研必须按固定阶段审批”的产品制度。此次验收链是代表场景，不要求每个项目都经历任务执行后才允许阅读或写作。

## 4. 建议交付结构

先区分三层文档：**总体需求保全表 → V0.1 发布计划 → 首科研迁入子计划。** 本报告的保全表可作为总体需求编号化的输入，迁入文件保留其具体接口与恢复测试。

| 顺序 | 交付内容 | 完成边界 |
|---|---|---|
| 第1交付：主体＋真实科研闭环 | 保留当前M1，补主体职责归属与最小上下文/工具/公共能力扩展契约 | 真包、真任务往返、笔记/结果/提纲、重开及两端记录；不要求完整Agent |
| 第2交付：既有科研全迁入 | 保留当前M2；非主链迁入可与第1交付并行 | 原功能矩阵逐项回归；明确LAN正式通信不在此冒称完成 |
| V0.1发布：科研能力补齐 | 全文检索、选定论文问答、研究卡、完整研究包接续；模型设置/公共服务及必要主体体验 | 原文命中可打开；答案限定资料且引用可核；卡可保存重开关联；研究包还原资料/引用；Mac/Android与Windows构建 |
| 后续明确交付 | 近期设备通信、完整询价、原型、基础记忆/后台整理、OCR/向量、选择器评估分别立项 | 顺序按价值和依赖确定；不强行在本次替用户排序，但每项有入口/owner/验收，区别于远期复杂同步 |

V0.1最小真实Agent体验至少能围绕当前选定论文问答并回源。完整跨模块工具自主推进不必因此强塞M1；若主对话先轻量落地有利于复用，可与上下文问答共用会话/模型服务。问答生成不能要求用户绕开MuSpace到外部模型工具才算产品功能。

优先补回发布范围和职责，不新增大型通用框架，不把记忆、IM、复杂同步全部推到首交付。已设计的单库事务队列、绑定与导入恢复应保留，它们是迁入可靠性的必要接缝。

## 5. 下一次计划修订的明确输入

1. 将现有迁入PRD/计划定位为子计划，恢复完整V0.1发布条件并调回询价相对优先级。
2. 以保全表给需求稳定编号，写清阶段/owner/依赖/验收；缺承接项标未规划，不宣称已有方案。
3. 补主体职责、上下文/工具/模型/执行记录和公共服务边界；最小契约先确定，功能按期实现。
4. 为正文检索、问答、研究卡、研究包及Windows构建建立具体实施任务和质量验证；近期通信独立承接。
5. 重新按“总体需求保全＋V0.1完整性＋M1可实施性”三层审查，避免只验证迁入技术路径。
