# MuSpace 设计文件研究

2026-10-03 · 分析基线：本仓 `1721735` · 本轮研究设计，不执行实施计划。

## 结论

**外壳复用现有领域模块的方向合理，但目前还不足以按实施计划直接交付完整 V0.1。** 最先需要解决的是接口闭合和上游交付门槛；随后补上问答质量、资源预算与用户操作的验收。继续增加框架、工具中心或未来能力不会解决这些问题。

这套文件已经明显超出概念草案：需求编号、模块责任、内容身份、修订冲突、权限、平台验收都有具体约束。主要不足是部分约束仍停留在文字承诺，没有贯穿公共接口和测试场景。以下发现均为**设计/计划缺口，不是已经观察到的运行故障**。

## 值得保留的设计

1. **业务事实由模块持有。** 外壳保存引用和目录，不建立第二套科研修订库，也不改询价规则（设计 35–43 行）。这有助于保持独立应用和原数据的连续性。
2. **内容、元数据与解析版本分离。** PDF digest、物理页、引句上下文、解析快照共同定位；改作者不破坏引用，解析不兼容时明确降级（设计 59–63、111–113 行）。
3. **权限与保存分开。** 模型出站范围授权和覆盖、删除、导出动作确认分别绑定具体内容；模型不能凭资料里的指令扩权（设计 105 行）。
4. **失败不会被总测试数掩盖。** 旧 HTTP 入口默认关闭；系统文件交换提供接续通路；fake 合同、真实模块和实机 release 分开验收（计划 221–227、245–256 行）。这些门槛应保留。

## 按优先级排列的发现

| 优先级 | 发现 | 置信度 | 判断性质 |
|---|---|---|---|
| P1 | 导出目的地、删除预览与确认之间的接口顺序未闭合 | 高 | 接口定义直接存在缺口 |
| P1 | 可取消流程与工作区切换缺少跨层异步合同 | 高 | 承诺与接口/场景覆盖不完整 |
| P1 | 卡片重开/编辑所需读取入口未明确 | 高 | 计划职责与公共端口不完整对应 |
| P1 | 问答验收主要证明引用可解析，尚不能证明回答得到证据支持 | 高 | 产品质量验收缺口 |
| P1 | 文件与模型处理的运行资源预算不完整 | 高 | 容量目标不能代替运行限制 |
| P2 | “存储/备份”页面承诺没有对应恢复规格 | 高 | 用户可见能力未落实 |
| P2 | 产品承诺和分期状态需要统一 | 中 | 文件状态与用户预期存在歧义 |

### 1. 导出与删除需要先把操作顺序定义完整

**证据：**计划 100 行的 `ExportInput` 要求 `destinationHandle`；149 行唯一列出的目标获取方法是 `savePackage(ArtifactRef, suggestedName)`，它已经要求有一个包。221–225 行又要求导出前按精确目的地确认。当前合同没有说明：先生成私有暂存包再选目的地，还是先选目的地再生成包。

删除也有类似问题：计划 101 行的 `DeleteInput` 强制包含 `actionToken`，106 行却让未确认前的 `previewDelete` 和确认后的 `delete` 共用它；233–237 行的流程是预览后才确认。

**推论：**实现者必须自行补接口或传占位目的地/令牌才能走通，容易使用户确认的内容与实际执行不一致。

**建议：**明确“私有暂存打包 → 预览 → 选择系统目标 → 绑定目的地确认 → 发布文件”的顺序，或者提供独立目标选择入口。将删除预览请求与已确认删除请求分开；预览结果应携带影响范围和修订摘要，确认后再校验是否变化。

**最小验收：**取消目标选择不发布文件；目的地改变必须重新确认；预览无需动作令牌；预览后出现新引用或修订变化必须重新预览。

### 2. 取消与工作区切换不能只靠关闭页面

**证据：**PRD 9 行、设计 89 行要求可取消。计划 102 行的调用上下文只有可选 `deadline`，197、209 行的 Gateway/PaperQa 接口仅返回 `Future`，没有明确的取消信号、请求句柄或调用失效机制。计划 139 行已有 `workspaceSwitchClosesOldContext`，所以切换并非完全遗漏；但未明确覆盖正在返回的模型、文件选择器和进度回调。

**推论：**关闭旧 session 并不能自动证明晚到结果不会显示在新工作区，或使用新的当前 binding 保存。截止时间也不足以表达用户即时取消。

**建议：**每次调用固定工作区、session 和内容版本，定义取消如何贯穿检索、模型请求、响应核验与保存。切换后的旧结果应明确选择丢弃或保留在原工作区；不得隐式绑定当前页面。已提交的结果仍按已有 committed 规则呈现。

**最小验收：**A 工作区提问后切到 B，再释放延迟响应；B 不显示、不保存 A 的结果。分别在检索中、等待模型、响应已到但未保存时取消；明确是否还会出站、出草稿或写卡。系统文件选择和阅读进度晚到回调同样覆盖。

### 3. 研究卡写入端口有了，读取闭环尚未说清

**证据：**计划 106 行的 `ResearchPort` 提供 `saveCard`，没有列卡、读取指定卡/修订的入口。计划 207–214 行却把卡页、离线手写卡、编辑既有卡和复开验收放在外壳任务中。D0 旧界面可覆盖旧 skill、任务和提纲，但文件没有明确它会提供新增研究卡的读取界面或 read model。

**推论：**实现者可能绕过领域服务直接查询业务表，或把内存草稿当作可重开卡片；这与模块唯一事实来源的原则不一致。

**建议：**明确 D3 提供卡片列表/详情 read model 或完整可组合卡页。若由外壳做卡页，公共端口应给出带范围、分页、指定修订和冲突 head 的读取能力。类似地，计划 161 行提到读取进度，但端口只列了保存，应明确读取由 D1 界面还是服务负责。

**最小验收：**重启进程后从实际模块读取原卡；编辑指定修订；并发两 head 都可见；缺失/已删来源状态正确；不能只用一次进程内的内存断言证明复开成功。

### 4. 引用正确是必要条件，问答有用还需要独立评测

**证据：**PRD R05（17 行）的重点是选择范围、可解析引用、无证据拒答和授权。计划 209–214 行核验 citation 标记和锚点。设计 85 行也准确注明：技术核验不证明科学论断正确。

**推论：**一个回答可能引用了存在的页，却把研究对象、实验条件或因果方向说反，仍通过当前主要技术断言。这里不应要求程序自动证明科学正确，而应补人评和失败样例。

**建议：**在现有 20 问基础上增加逐论断的证据支持、答案覆盖和必要限定条件评审。纳入同主题但不同实验、否定结论、相互冲突论文、只有局部证据的题。将“引用已核验”与“人工已审阅”分别标识，避免裸露 `verified` 被理解为答案正确。

**最小验收：**引用真实但不能支持回答的样例不能被计为质量通过。质量集与开发调试题分开；分别报告检索召回、引用范围正确、论断支持、拒答和人工可用性，不能用一个总分替代。

### 5. 容量基准不等于处理预算

**证据：**PRD 9 行列了 200 PDF、2GiB、150MiB 包等目标；设计 109–111 行要求复用路径、大小、hash 校验。计划 97 行限制 hits 数，104 行模型请求只列 `modelId/messages`；未给出问题/片段长度、请求与响应上限、输出预算等合同。

**推论：**20 条命中不保证请求足够小；150MiB 包也不能单独限制展开后的文本、文件条目数量或解析占用。现有模块可能已经有部分保护，本轮没有查其实时实现，不能断言完全没有防护；缺的是新增科研包与模型通路统一可核验的预算。

**建议：**文件合同规定压缩输入、展开总量、单条目、条目数、manifest/文本字段及暂存磁盘预算，明确流式验证与失败清理。模型合同规定问题和片段预算、请求/响应字节、超时和支持时的生成上限；裁剪必须保留引用对应关系，不静默破坏证据。

**最小验收：**高展开量包、多小文件、超长文本、超大模型响应、空间不足、预算裁剪后引用一致性。阈值根据目标手机实测确定，不把建议容量直接当安全边界。

### 6. 备份与恢复需要明确是否属于首版

**证据：**设计 131 行“我的”包含“存储/备份”；47 行要求旧库迁移前备份。PRD R09 的恢复断言主要是 staging 对账；计划 250 行仅说明备份/export 范围，没有备份创建、恢复、格式或迁移回退任务。

**推论：**研究包只包含用户选定资料，不天然等于整个工作区可恢复备份；staging 恢复也不能替代误删、损坏或迁移失败后的恢复。

**建议：**若首版只有研究包导出，页面明确称为资料导出并将完整备份后置。若保留备份承诺，先规定外壳和模块的协调快照、绑定映射、附件完整性、恢复预览及失败时原库保全；端点凭据和授权不要随普通资料包自动恢复。

**最小验收：**在空安装恢复后对象/修订/附件一致；坏备份不得部分覆盖原库；迁移失败可回到可读旧库；恢复后的模型凭据与授权重新建立。

### 7. 首版承诺与文档阶段应统一

**证据：**设计 9 行以“个人 AI Agent 为核心”描述产品，实际 15–17 行首发科研、询价等后置；计划 22、209–213 行采用非工具调用的一次检索/一次生成流程。主规格 3、13、156 行和 PRD 27 行仍写待审/确认后才写计划；计划 11 行则记录已批准进入计划。

**推论：**前者可能让用户期待跨业务自主行动，实际交付是科研工作台和限定问答。后者不证明历史批准无效，但读者无法仅凭文件标题判断哪些决定已批准、哪些仍待定。

**建议：**用具体首版价值作为描述：Mac/Android 离线阅读整理、选定论文问答、显式研究包接续。保留 Agent 路线，同时写清本版可执行动作。增加统一状态表，记录规格基线、已批准决定、计划状态和未决分期，保留历史快照原文，不让旧“待审”充当当前状态。

## 依赖与推进建议

**证据：**计划 42–46、266 行已经明确承认 D0 组合模块包和 D1–D3 领域能力未交付确认。矩阵 29、47 行也将全文检索/进度/精确卡与新包标为缺口。这不是本次新发现的设计错误，但它是当前交付的关键路径。

建议按以下顺序推进：

1. **先闭合合同。** 修正导出、删除预览、取消、卡读取与进度读取，并把上述最小场景加入计划。
2. **明确 D0–D3 实际交付。** 为每项记录负责人、不可变版本、真实公开入口和验收状态；不要把旧阅读计划自动当成新增卡/包/清理服务的承诺。
3. **尽早验证一条真实双端纵向流程。** 从实际模块导入 PDF、离线保存笔记/手写卡、系统导出、手机导入、回到原页、重复导入和重启复开。它能尽早检验组合与数据身份；mock 外壳工作可并行，但不代替这条证据。
4. **再接全文检索和模型。** 先证明范围与引用，再评测答案质量和手机预算。TLS/IM、向量、OCR 继续按已有独立门槛推进。

没有应用代码，因此本轮不运行产品 lint、构建或测试，也不宣称上述建议已实现。当前成果是一份可用于下一次设计修订和计划评审的研究报告。
