# 首字与卡片出现延迟的静态调研（CR-5，ChatGPT 6 Pro）

依据固定：R = `86525cd`（现有首字路径与 E-1 测量）；P = PR42 `c7bbc94`（生产卡片接线）。只读静态代码，未运行任何测量；**耗时排名全部是推测**。原稿由用户转交，leader A 整理入库，保留结论、路径、瓶颈、测量方案与待决事项，代码位置以原稿为准。

## 总判断
首字与完整卡片都有明确的串行等待，但现在不能判断是否达标。按 PR42，流式编译期间只显示「界面接收中 · N 个节点」，完整卡片要等规划模型正常结束、账本与子任务收尾、最终校验和界面绘制。最该先测：**第二次（规划）模型请求、每个增量的宿主快照复核、同步数据库查询与界面刷新**。

## 1. 点击发送 → 首个可读文字
「首字」定义：主回答里首段非空、可读的模型文字实际显示（允许是草稿），不计「正在思考」、审批说明、JSON 符号、卡片接收状态。
串行路径（R）：接收发送与建会话 → 构造并冻结任务输入（同步 CPU + SQLite 读，读全部历史后取最后 16 条）→ `createTask` 与 `appendMessage` 两次有序写入 → 预算与上下文压缩 → 可选的规划元数据 `planning.source`（无超时）→ 请求预览、大小检查、digest、策略 gate → 授权审查与自动 / 人工分支（人工停留无固定时长）→ 凭据读取、`beforeSend`、`ledger.begin`（严格串行，不能先发后记）→ 建连、请求、SSE 解码 → **首个模型事件到达后先 `await` 写一条 `modelRequest` 事件** → 协议视图只暴露合法 `answer` 文本、`DraftFeed` 发布 → 页面重建与绘制。
- 数据库写入是排队后同步执行 `BEGIN IMMEDIATE → body → COMMIT`，不是后台线程。
- 三个会显著改变路径的分支：(A) 长上下文可能先跑一轮用户看不见的摘要模型请求；(B) 工具型问题可能多轮后才出正文；(C) 调用 `chatStream` 但 profile `streaming=false` 时仍是整包返回。`DraftFeed` 首次变化立即发布，80ms 合并不是固定附加，但空前缀可能让首个非空答案落入合并窗口。

## 2. 回答完成 → 完整卡片（P）
先判断该不该出卡：默认 `textOnly` 不规划；`few` 只认宿主显式入口；`automatic` 仍要求 source 可用（当前生产 source 要求选定的询价对象，普通全局聊天可能直接 `host_state_unavailable`）；provider 要求模型开启 streaming。
路径：原回答提交 → 规划资格、source、去重 → 构造规划请求（guides 有 2 秒超时但默认空源，不是每次固定等 2 秒）→ 建 stream session 与内部规划子任务 → **再走一遍完整模型请求链** → **每个 `TextDelta` 先重读 source 复核**（SQL、JSON、哈希、范围检查）→ 按换行拼行、编译、每行发布进度并 `repository.refresh()` → UI `end` 整树校验 → 模型 `[DONE]`、账本 finish、子任务提交 → harness 再校验并多次读 source → widget 再读 source、复核 pins、装 controller → 首帧。
- UI 的 `end` ≠ 模型 `[DONE]`；末行无换行时要到 `requestModel` 返回后才处理。
- 当前「流式预览」不是逐步成形的卡片，只是节点计数文字。至少分测：规划状态首次显示、首节点编译、完整卡片首帧。
- 15 秒规划超时只包住 `provider.plan`，前后的 source、校验、安装和取消清理都在外面，所以「回答完成 → 卡片或退路」可以超过 15 秒。

## 3. 可能的瓶颈与低风险方向（均为推测）
| 优先级 | 瓶颈 | 方向 |
|---|---|---|
| 高 | 第二次规划模型请求；长上下文前置摘要请求 | 分开记录 caller 与耗时；规划输出用紧凑卡片，少无谓节点与 patch，必需事实不省 |
| 高 | 每个增量重读 source | 先拆 SQL、范围解析、哈希、JSON 成本；可优化单次复核内的重复投影与编码；不删、不降频、不绕过当前性检查 |
| 中高 | 每行重复计算 compiler 完整 current view（随行数 × 节点数增长） | 复用同一次 mutation 的结果；保留原始候选、错误集合与 end 整树校验 |
| 中高 | 全量历史与任务查询、随刷新重复读取（`tasks()` 读全部后在 Dart 过滤） | 等价语义缩小查询；发送窗口优化与授权事实的完整检查分开 |
| 中 | 每行全局通知、整页重建、卡片反复重装 | 只合并非权威的进度通知（按帧），失效 / 撤权 / 失败 / 终态通知仍及时 |
| 中 | 首事件后的事件写入、多个串行事务 | 先测队列等待与事务执行；不改成 `unawaited`，不提前显示绕过顺序 |
| 中低 | 兼容协议字段顺序与草稿合并 | 提示先输出 `type`；首个非空正文立即发布 |
| 待分段 | 建连、凭据读取、非流式兼容重试 | 先核实际 capability 与 SSE 行为；连接复用测出占比后再评估；不缓存长期密钥 |
不调整授权、确认、出站账本、业务回执、事务提交与取消清理的顺序。

## 4. Haiku 冒烟与 E-1 共用测量方案（设计，未实现）
- 旧指标不是 UI 首字：`first_byte_ms`（记账后到首个 body chunk）、E-1 `request().ms`（整包）、`firstEventMs`（任意首事件）、`firstResponseMs`（首个成功调用）。E-1 环境入口不传 capabilities；空样本分位数返回 0 应改为「未观察到 / 不适用」。
- 每次提交一个随机 `trace_id`，每个回答 / 摘要 / 规划请求与重试一个 `attempt_id`，单调时钟。打点：`submit_accepted`、任务构建、两次写入、`db_enqueued / transaction_begin / commit_done`、压缩、预览 / 审查 / 落盘、确认可见与确认进入、凭据与账本、建连 / 响应头 / 首包、首模型事件 / 首文本 / 首工具片段、请求事件落盘、首个可显示文本 / 首次非空发布 / 首文本帧；规划侧：答案提交、规划入口、source、guides、每增量复核、编译块、首 UI 行 / 首节点 / end 解析 / end 校验、模型结束、账本结束、子任务提交、`requestModel` 返回、harness 校验、呈现发布、widget 复核、controller 安装、完整卡片帧；超时 / 取消完成 / 退路发布。
- 首帧落实到界面：本次任务、非空、在可见区域、是最终 `DynamicUiSurface` 而非节点计数；长历史固定滚动位置。E-1 无界面时首帧两项标「未测」。
- 指标：用户首字 = 首可读文字帧 − `submit_accepted`；自动规划完整卡片 = `full_card_frame − answer_committed`；显式规划 = `full_card_frame − 点击「规划此回答」`；收尾 = `full_card_frame − model_done`；宿主时间 = `full_card_frame − request_model_returned`；机器处理口径扣除明确记录的人工确认区间（按时间并集）。`assistant.plan_ui` 触发另标 `trigger=model_tool`。
- 次数：Haiku 冒烟每场景 2 次预热 + 10 次正式（报中位数、最小最大、成败数，不宣称 p95）；E-1 定位每场景 3 + 30（中位数、探索性 p95、阶段占比）；正式尾延迟每配置约 100 次（p50/p95、超时率、失败率、重试率、超阈比例）。固定 SHA、设备、构建模式、模型、capabilities、输出预算、种子、历史长度、规划输入；覆盖 native/compat、流式 / 非流式、工具先行、压缩三态、三档、本机 / 远程、冷热、规模对照。失败、取消、超时不删不记 0；textOnly 等不适用单列。
- 日志白名单：可记 SHA、设备与构建标识、场景 ID、随机 ID、caller、轮次、声明能力、字节 / token 数、节点 / 行 / patch 数、阶段耗时、固定状态码、重试 / 压缩标记；不记密钥、`credentialRef`、请求头、prompt、模型原文、工具参数与结果、卡片内容、业务对象 ID、完整 URL；端点用脱敏别名；增量测量内存累计、结束汇总，不新增逐 token 数据库写入。

## 5. 卡片可见延迟目标（待用户决定，均为建议）
| 指标 | p50 | p95 |
|---|---|---|
| 本机小计划：完整卡片延迟（自动从答案提交计，显式从点击计，人工确认另列） | < 1.5s | < 3s |
| 远程小计划：完整卡片延迟 | < 3s | < 6s |
| 规划请求完整返回 → 完整卡片首帧 | 先记基线 | < 250ms |
| 已接受规划 → 首次进度反馈 | 先记基线 | < 200ms |
小计划基准：8～16 节点、深度 ≤ 4、≤ 24 条 NDJSON、≤ 8KiB、patch ≤ 2、6～10 条可信事实；只是实验分组，不改协议上限。理由：完整卡片要多一轮模型生成，中位额外等待与首字目标同量级，p95 约两倍；单列 250ms 宿主收尾以区分模型慢与宿主慢；慢请求与失败分开，不为达标提前授予 renderer 能力或跳过校验。

| 待决定 | 推荐 |
|---|---|
| 「卡片可见」完成点 | 通过最终校验与宿主复核后的正式卡片进入可见区域的首帧；节点状态与首节点另计 |
| 是否采纳小计划阈值 | 先作为待验证目标：本机 p50 < 1.5s / p95 < 3s，远程 p50 < 3s / p95 < 6s，首轮基线后再调 |
| 人工确认时间 | 同时保留完整用户等待和扣除人工停留的机器时间；性能目标看后者 |
| 既有首字 1.5s / 3s 口径 | 不改写原标准；建议后续明确分位数、样本条件与超出比例，Haiku 与 E-1 共用 |
