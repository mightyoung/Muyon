# 写卡实现前的通用写工具差距审计（CR-11，ChatGPT 6 Pro）

审计基线：develop `1e67147`（复核未变）；设计依据 `task/decisions-20261011c` @ `c4ef59a`（CR-2 D1～D11、GB-5 W1～W6、CR-6 B1～B5 已采纳）· 只读 GitHub，未运行测试 · 原稿由用户转交，leader A 整理入库，代码位置以原稿为准。

**结论：** 四个通用写工具可保留，但还不满足直接接写卡与原子批量的前置：须补同源可写声明、完整只读校验、结构化冲突、强身份业务回执查核，并把单行领域逻辑与事务、回执、通知编排分离。恢复要走独立只读查核路径，单纯调整原写 handler 顺序不够。

## 1. 改动位置
- **片 B 可写声明与完整预检**：`muyon_module_api` 的 `ModuleFeature`（只有五项）与导出新增可选接口（片 A 先定稿）；`inquiry_module.dart:35-43,113-131` 新增能力实现与「声明与实际接口一致」的宿主检查；`inquiry_record_tools.dart:11-40` 的类型、保护字段、报价五字段白名单抽成「类型 × 操作」可写声明，工具 preflight 与写表单同源；`:74-181` 跨类型 schema 与 `_validateArguments` 抽取共享（不能当完整预检）；`:415-489` 目标状态、版本、默认值、基线合并、规范化、项目归属、恢复依赖、删除引用预览抽成只读「单行候选准备」，执行时仍重读真实状态；`store.dart:387-435,553-670` 的完整领域检查（报价编辑、预算快照、项目价格口径、产品单位换算、引用例外）抽成只读检查，Store 原行为不变。
- **「包装一次 `validatePayload`」只能作起点**：它只是按实体 `fromJson().toJson()`，依赖数据库与旧记录的规则在 Store 里。字段定位需补上下文：`ExactDecimal.parse` 统一用字段名 `decimal`，`project.dart` 的 `_decimal(value, field)` 没把错误绑回实际字段；改为结构化校验结果 + 稳定错误码，无法定位时返回表单级错误，不伪造字段路径。七类型枚举不等于七类型都可创建（报价白名单缺价格等必需字段），能力声明须表达。
- **片 C 结构化冲突**：选中快照或工作区变化 `:218-230`；同 ID 换参数或范围 `:400-414`（明确身份冲突，不混为未查到）；目标状态或 `expected_version` 不符 `:417-424`（保持 `failed`，附错误码与允许披露的当前版本）；删除引用预览不完整 `:469-488`（批量另绑 `row_id`）；最终出口 `:527-532` 与 `app_state.dart:687-695`（共享错误类型，避免先压成友好文本再由宿主猜）。错误转换必须在最外层事务之外（`Store.transaction` 正常返回即 COMMIT）。`ToolCallStatus.failed` + `data` 已够，不加新状态；批量另需失败阶段、行身份、整批未提交证明。
- **片 D 业务回执与恢复**：抽取共享 `:380-414` 的身份构造、`reg4c:` 查询与匹配；`:501-524` 新增版本化回执形状（现只存 `arguments` 与 `result.toJson()`）；`inquiry_module.dart:113-149` 现有 `receipt(operationId)` 属导入流程，不能代替；`tool_registry.dart:1066-1085` 的 `receiptFor` 只读宿主回执、`agent_resume.dart:244-290` 不查 `reg4c:`，需新接线。**GB-5 草案 `lookupBusinessReceipt(String operationId)` 不能直接定稿**：须绑原摘要、工具、范围、领域库身份，并区分匹配提交 / 身份冲突 / 未发现 / 不可读 / 未知。
- **CR-6 原子批量**：新增 `inquiry.atomic_batch_write`、能力声明与覆盖清单；新增执行前持久的 `operation_id → batch_digest` 绑定（现 `reg4c:` 只在成功事务内插入，不满足「首次失败后同 ID 仍禁止换内容」）；顺序改为一个外层事务、先查全部候选与批级约束、再应用、写整批回执、最终提交；新增提交资格复核与未知结果查核。不能靠改现有顺序批卡文案表示完成。

## 2. 共享抽取边界
共享两类：候选准备（读基线、目标与版本、合并默认与 patch、规范化、范围与引用、完整领域检查 → 候选与诊断）与单行应用（在调用方事务内保存 / 删除 / 恢复，保持版本、日志、触发器）。留在入口编排层：取消检查与 `activateInquiry()`（`:361-370`）；`_currentSelection` 整集合复核的时点（逐行只查本行目标与引用，第一条变更后不再用原快照复核整批）；`call.checkBeforeEffect()`（`:490-500`，批量另需最终提交门）；单条 `reg4c:` 查询与插入（批量写整批回执）；`state.write` 的关闭检查、友好错误转换、通知（批量提交后统一通知，只读校验与查核不调用）。
必须保留的隐藏耦合：(1) 候选组装顺序有业务含义（先全字段默认 → 覆盖旧记录 → 覆盖 `values`，未提供保留、显式 `null` 才清空，更新带 `allowClear: true`），不能把未提供变成 `null`；(2) Store 与助手工具删除 / 恢复规则不同（`Store.delete` 无入引用阻断，`Store.restore` 允许部分未变旧引用指向软删记录；助手入口额外要求「有活跃引用不能删」「恢复依赖先存活」，`inquiry_general_write_tools_test.dart:460-505` 专门证明这一点）；(3) 旧业务回执身份用原始参数（递归排序键、列表保序、范围身份不含 revision/digest、含原 `expected_version`），换成新规范化指纹会改变旧 `operation_id` 匹配语义——旧回执保留旧规则，新批回执用版本化协议；(4) 「没有实际改动」现在仍会写（工具只拒空 `values`，`Store.save` 值相同仍增版本），写卡显示「无需保存」、CR-6 拒空更新，但塞进共享应用函数会改变旧单条行为，须作为显式语义变更；(5) 写入还触发 FTS、宿主变更日志与 `Store._floor` 内存逻辑时钟，所以直接抽只读检查，不用「先 save 再回滚」做预检。
提前赋值成功结果：`:503-520` 先构造 `succeeded` 再编码插入回执，`:528` 只看 `result != null`，非空 result 不是提交证明。**推测（条件性）**：若以后在赋值后、提交前加入会抛 `FormatException` 的检查，事务回滚后异常可能被 `AppState.write` 转成字符串而 handler 仍返回成功；本次未确认现有路径能触发，不宣称现存故障。抽取时明确区分「最外层事务已成功返回」与「提交后通知失败」。

## 3. 恢复顺序
现顺序：参数校验（`:375`）→ 整个选中快照的身份 / revision / digest / 工作区（`:376`，实现 `:218-230`）→ 目标属选中集合并构造业务身份（`:379-399`）→ 查 `reg4c:`，匹配即返回（`:400-414`）→ 只有未命中才查目标状态与 `expected_version`（`:415-424`）。CR-6 说的「先核当前版本再查回执」准确指**选中快照检查在前**。现有重试测试（`inquiry_general_write_tools_test.dart:140-180`）每次经 `request()` 重新解析当前 selection，验证的是「最新快照 + 原参数命中回执」，不覆盖「保留原冻结快照恢复」。更早的宿主范围检查也会挡：`Registry.invoke` 先 `prepare` 解析范围，`ScopeResolver` 比较版本与摘要，原更新提交后旧 scope 可能进不了 handler。
建议：单条入口区分「读取历史提交结果」与「准备新写入」；完整恢复由片 D 承担：核读取资格、原业务身份与原摘要 → 查历史回执，匹配则返回提交时结果（不要求目标仍处写前版本）→ 未命中先区分仍在执行 / 未知 / 不可读 / 已证实未提交 → 确需新执行才走完整的当前 scope、版本、引用、授权、取消检查 → 保留 Registry 普通写入的过期范围与审批失效规则。保持「最新 scope + 原参数命中回执」与「无匹配回执时旧 `expected_version` 仍拒绝」（`:245-258`）两条现有测试；新增旧基线只读查核、提交后再次修改仍返回历史结果、领域已提交而宿主终态缺失的恢复测试。

## 4. `ToolCallResult.changes` 不进 JSON
确定影响：持久化往返丢失带 upsert/delete 语义的变更清单（`tools.dart:55-120`；`contract_v2_test.dart:127-144` 明确断言 JSON 不含 `changes`）。`reg4c:` 业务回执本身就存 `result.toJson()`，所以业务回执层就丢了；宿主调用回执同样没有，但 status、data、objectRefs 保留；当前 Agent 恢复按回执身份与状态采纳结果并合并 `objectRefs`，不依赖 changes。不能据此断言索引 / 投影停更（`ProjectionService` 从持久 `ModuleChangeLog` 按游标同步）。建议版本化业务回执显式保存变更清单，保留通用 `ToolCallResult` 现有 JSON 契约；旧单条 `reg4c:` 核验身份与完整性后可按 `data.type/id/version/deleted` 与 `objectRefs` 兼容恢复，不能把任意工具的所有 `objectRefs` 当已修改对象；批量必须存逐行映射与完整清单。

## 5. 实现顺序与先补的特征测试
**先补旧行为特征测试 → A → C / D（可并行，改同一 handler 时划清范围）→ B 分步抽取 → CR-6 独立批量 → E → F。** GB-5 的 F 是科研可选接入，原子批量另列。
- **A 契约骨架**：v1 与不声明新能力的 v2 模块照常；feature 与接口都具备才调用；声明、草稿、规范化结果、issues、回执的嵌套数据不可被调用方事后改；**回执查询首版就要强身份、强摘要、明确状态**，缺证明不认成功；保持 `failed + data`，旧 JSON 缺新字段有兼容规则；单条写表单能力不推导原子批量能力；保留现有 `changes` JSON 契约测试。
- **C 冲突**：版本、选中快照、引用预览、operation ID 重用各有稳定诊断，改摘要文字不改宿主分支；冲突后 payload、版本、删除状态、日志、业务回执都不增加；真正构造「引用对象版本已变化」的删除预览用例（现测试名含 stale 实际只传空列表）；无读取资格不返回当前对象详情；结构化包装不让旧审批重新生效；事务内以异常中止、外层转 `failed + data`。
- **D 只读回执与恢复**：更新已提交后持原 ID、原摘要、旧基线查到提交时结果；对象再改仍返回原回执版本；领域提交后宿主终态丢失、重启查核不产生第二次写；同 ID 换参数 / 范围 / 工具 / 领域库明确冲突；未知、不可读、损坏不当未提交；旧调用仍在运行或等锁时未查到仍未知；lookup 前后业务库、日志、审批、调用回执、通知计数都不增加；新旧回执恢复策略都有测试。
- **B 先抽候选准备，再抽单行应用**：同一基线与 patch 预检与事务内执行得到相同规范化结果与结论，预检无写入 / 回执 / 审批 / 通知；未提供、`null`、空串、零、false、空列表各保语义；保护字段与报价 metadata 边界保持，报价价格与授标快照逐字段不变；历史联系人例外、预算价格口径、单位换算、项目归属、删除恢复额外约束进共享候选测试；非法十进制定位到实际字段，否则表单错误；应用、日志、回执失败传到最外层，提交前不通知，提交后通知异常不改写提交事实。可复用基线：`inquiry_general_write_tools_test.dart:509-529`、`store_test.dart:58-94`、`project_basis_test.dart:12-45`。
- **CR-6 批量**：最后一行版本冲突第一行也不写；第 N 行写 / 日志 / 回执编码插入失败整批回滚；专门识别「helper 返回普通失败而外层提交」与「嵌套事务返回即报成功」；同模块类型操作范围领域库与预算检查；重复对象与批内依赖拒绝；同 ID 同内容最多提交一次，首次失败后换内容仍冲突；提交门前取消可证明回滚，提交后取消保持提交事实，未知不换 ID 重发；恢复全部行、真实 ID 映射、版本、删除状态、变更清单，失败结果不夹带 applied。回滚检查比较业务行、版本、领域日志、模块日志、索引、回执。现有批卡测试（`agent_batch_card_test.dart:241-286,394-420`：三调用、三审批、三回执、失败只阻后续）作为顺序执行语义继续保留。
- **E 宿主写卡接线**：本体、可写声明、编辑器能力、权限取交集，缺能力不可提交；校验失败不批准不调用，晚到校验不覆盖新草稿；编辑 → 规范化 → 差异 → 确认 → 调用 → 业务回执闭环，版本只加一次；确认后业务值、成员、引用、范围、规则版本变化使确认失效，纯视图变化不改业务摘要；冲突按结构化数据处理，未知走 D 不重新 invoke；外部 / 未知污染不进原子批量，逐项入口不可用时不伪装可执行。现有本体卡「提交禁用、记录不变、回执为空」与草稿恢复「operation unknown、业务调用零」测试继续作边界基线。
- **F 科研可选接入（后置）**：不声明 `writeForms` 时保持既有科研能力；每个开放操作绑真实具名工具，不从询价模板推统一 CRUD；按实际 revision / digest 规则查基线，无回执能力保持未核实；导入回执不能充当写卡回执；单条写表单不自动开启科研原子批量。
实施门槛：单条写卡接线至少等 A～D 的契约、完整预检与恢复验收；批量写卡还须等 CR-6 的真实原子性与故障恢复验收。
