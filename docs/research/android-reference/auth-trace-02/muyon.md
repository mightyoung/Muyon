# 对 Muyon 的启示（不修改代码，也不改两本设计书）

## 可以借鉴
1. **先认领、后执行，并补上 Claude 缺的部分**：
   - 账本主键用 action_id，同时存 params_digest（规范化 JSON 后取 SHA-256，参照 ChatGPT 的 o3z0.p）、对象 ID 和版本、状态。
   - 状态流转：claimed → sent → receipt_saved / unknown。
   - 出现 unknown 时先核对。不要像 Claude 那样直接按"不可用"回给模型。
2. **复用授权或确认前，先比对摘要**（参照 ChatGPT hdb0）：同一个 action_id 但参数不同 → 拒绝，并要求重新确认。
3. **不允许的工具在发请求前就剔除**（参照 Claude e8z），同时在执行前再检查一次（参照 k8z.r）。宿主确定性授权要两个点都做。
4. **嵌入界面的来源绑定到连接器**（参照 Claude qkk.d）；生成式卡片只能用白名单动作（参照 ChatGPT DIL，符合已决定的第 2 条）。
5. **审批过期**：消息或轮次结束时，没回答的审批自动失效（参照 Claude yla.g）。

## 对照你提出的设想，残余风险
- **"全部允许"跳过新站点/新 API 的首次确认**：三款产品都没有足够证据，来自官方说明的反例更多（ChatGPT 的站点授权和重大操作确认是分开的）。建议：在"全部允许"下仍然做目标地址的确定性校验（解析结果、限定范围），并记日志。
- **业务按钮直接提交受控命令**：要绑定按钮出现时的对象和版本，否则会出现 Claude 通知栏审批那样只靠 ID 绑定的问题。
- **撤权**：三款产品都没看到撤权后正在执行的任务怎么处理。Muyon 需要自己定义。

## 负向验收用例
1. 同一个 action_id、不同参数：拒绝，不执行，提示重新确认。
2. 执行后、保存回执前进程崩溃：重启后状态为 unknown，先核对再显示；不重复执行，也不直接写成失败。
3. 卡片尝试触发有副作用的动作：被宿主拒绝，并记录日志。
4. 审批卡片对应的对象版本已变：确认按钮失效。
5. 撤权后立即重放旧的确认：拒绝。
6. "全部允许"模式下请求外泄（数据发往未授权目标）：仍然被禁止规则拦截。
7. 没有审查器或审查超时：高风险动作默认走询问或拒绝，不能默认放行。
8. 对同一个动作并发点击两次：只认领一次，第二次拿到原回执。
9. Stop 时动作已经发出：显示"已发送·待核对"，不能显示"已取消"。
