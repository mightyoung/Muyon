## RALPLAN-DR
原则：首业务闭环先交；完整版本范围可追溯；公共机制单实现、领域单一事实；离线和明确数据去向；验证不夸大。
驱动：保留全部需求、尽快真实科研可用、后续模块可复用。
选项A：迁入子计划+完整版本增量+总体账本，能保早交付与范围追踪，代价是维护三层映射；选择A。
选项B：一个大计划覆盖所有总体能力，文档入口少，但易把IM/记忆/询价堆到首版，反馈慢；不选。
选项C：只交迁入，其他名词留愿景，最快但不满足明确V0.1发布要求；因需求不符不可采用。

## 三项失败预演
1. M1被当V0.1完工：独立V01–V09停止条件，需求账本映射；verifier按三层分别判定。
2. 检索/问答命中旧或越界资料：索引身份/失效+发送前领域复核+结构引用允许集；注入删除/换项目/换端点测试。
3. 研究包或并发卡覆盖人工修改：冻结清单/原文hash/修订父与expectedHead，分叉不覆写，导入事务失败及跨设备冲突测试。

## 验证与交接
计划阶段仅验证文件链接和需求映射。执行阶段在每目标Flutter包跑flutter analyze/flutter test；app运行 `flutter test integration_test/v01_research_journey_test.dart -d <id>`（Mac/Android分别）；`flutter build macos --release`、`flutter build apk --release`，Windows环境执行 `flutter build windows --release`。记录Flutter/插件/模型/语料/设备版本；缺环境不安装或伪报通过。先交M1、M2成果，再V0.1；后续具名F阶段见账本，未获得执行handoff不进入代码实现。
