# 审查任务通用清单

所有审查由 leader 执行。任务完成后，leader 从任务分支的最终提交建立审查分支 `review/<任务编号>`，按本清单审查，把结论写入该分支的 `docs/tasks/<任务编号>-review.md`。需要修改时，执行者检出审查分支，按结论修复并提交在该分支，leader 复审。本清单同时是执行者的自查清单：提交前先按「必做」逐项自查。

## 代码核实由子代理执行

leader 不在主线程里运行或通读代码。凡需要重跑 analyze 与测试、逐行阅读 diff、检查边界与安全的核实，由 leader 派给核实子代理：

- 默认派 Sonnet 5.5，按难度选思考强度（子代理 `reviewer-sonnet-low` / `-medium` / `-high`，定义在本机 `~/.claude/agents/`）：安全边界、并发与取消、数据一致性、跨模块改动用 high；单模块代码与测试补充用 medium；脚本、文档、证据字段核对用 low。Opus 只在 Sonnet 结论有分歧或问题特别难时使用（用户 2026-10-06 要求）。
- 也可以**交叉派给执行者**，前提是审查者不是该任务的作者：engineer（Sonnet，本机，有 Flutter）与 junior（opencode，本机）可做构建与测试类核实；engineer2（grokbot，云端，无 Flutter）只做静态核对与文档审阅。交叉审查同样按本清单回报，leader 据此下结论。

核实子代理的工作方式：

- 在 leader 建好的独立工作区（审查分支）中工作；
- 按本清单「必做」逐项执行，只回报命令输出、核对表和发现；
- 不提交、不推送、不修改代码。

leader 根据核实报告写出审查结论与修复要求。

## 必做

1. **范围**：`git diff --stat origin/develop...HEAD` 对照任务说明的「交付」与「约束」，列出任何超出允许范围的文件。
2. **逐项核对交付**：任务说明里每一条交付、每一条完成判据，写明「满足 / 不满足 / 部分满足」及依据（文件与行号）。
3. **亲自重跑验证**：执行任务说明「验证」一节的命令，贴出摘要行。不采信执行者的自述。
4. **测试质量**：测试是否真的断言了行为；有无空断言、靠 `sleep` 的时序、依赖网络或机器负载；有无修改已有测试来换取通过。
5. **安全**：密钥是否可能被打印、记录或写入文件；是否有未声明的外部请求；授权与审批是否可能被绕过。
6. **证据诚实**：夹具或模拟结果是否被写成真实模型、真机证据；报告与文档中的数字是否能由命令复现。

## 结论分级

| 级别 | 含义 | 处理 |
|---|---|---|
| 阻断 | 错误行为、安全问题、验证失败、证据不实 | 必须修复后才能合并 |
| 应改 | 正确性边界、可维护性、测试缺口 | 本轮修复，除非说明理由 |
| 可选 | 风格、命名、措辞 | 记录，不阻塞 |

小而确定的修复（几行以内、不改变设计）由 leader 直接在审查分支提交，提交说明写明对应哪条结论；其余修复交回执行者。设计层面的问题先与用户确认，再决定是否改。

## 回报格式

- 审查分支与最后提交；
- 范围检查结果；
- 交付逐项核对表；
- 重跑验证的摘要行；
- 结论列表（级别、文件:行、问题、建议），以及已在审查分支提交的修复；
- 是否建议合并。
