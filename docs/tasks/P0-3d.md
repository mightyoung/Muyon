## 执行记录（senior，2026-10-06）

基于 `review/P0-S1`（`3b237d7`，用户要求不等 P0-S1 合入）。

### 根因
- 助手请求不带 `response_format`：`OpenAiModelGateway.chat` 只发 `model`、`messages`、`stream`。协议只写在系统消息 JSON 的 `instructions` 英文句子里："Return one JSON object…"。
- 工具结果作为 `role: user` 的 `trustedToolResult` JSON 回给模型，其后没有任何格式提醒，deepseek-chat 容易直接用自然语言回答。第 1 次失败就是这样：预算题的答案"成本合计 2080 元"，数字正确，但是纯文本。
- 工具清单只在系统消息里，请求本身不带 `tools` 参数；deepseek-chat 看到工具清单后，有时会输出自己的原生调用标记 `<｜｜DSML｜｜ calls>`。第 2 次失败就是这样，第一轮就输出了这种标记。
- O1：工具成功后，任务的 `summary` 写的是工具说明文字；模型随后失败时它没有被替换，链路脚本却把它当作回答预览。

### 做法与理由（两者组合）
1. 请求 JSON 输出：网关对 `caller == 'assistant'` 的请求加 `response_format: {"type": "json_object"}`，系统提示里已有 "JSON" 字样。
   - 端点返回 400 或 422 时，去掉参数重发一次同样的、已确认的内容，并按"端点 + 模型"记住，之后不再带这个参数。两次请求都进账本。
   - 用 `caller` 开启而不给 `chat` 加参数，是为了不改动已有测试中覆写 `chat` 的假网关。问答、整理等其他调用方不受影响。
2. 至多一次纠正：回复不是严格的协议 JSON（纯文本、DSML、JSON 形状不对）时，追加一条纠正消息，走正常的模型确认流程发起新一轮。
   - 新一轮计入 `maxRounds`，经网关、进账本。
   - 被丢弃的回复不保存、不回传。
   - 纠正后仍不合规，任务失败，原因是固定文字 `model_reply_not_json` 或 `Invalid assistant protocol`，不引用模型原文。
3. 安全：只认整段文本是协议 JSON 的回复。不剥离代码块，不从文本里提取 JSON，不解析 DSML。不合规的回复不会变成工具提议，也绕不过确认。
4. O1：只有任务成功时，`answerPreview` 才取 `summary`；证据里另外记录 `protocolCorrections`。
