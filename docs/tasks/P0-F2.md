# P0-F2 修复 research_object_open_test 的两个 10 分钟超时（develop 门禁变绿）

分支 `task/p0-f2-object-open-timeout` · 执行 junior（opencode）· 审查 leader · 依赖：**E11b 合入之后开始**（同一个测试文件），开始前 `git merge origin/develop` · 排在 P0-J3 之前

## 背景
`apps/muyon/test/research_object_open_test.dart` 中两例在干净 `develop` 上失败，CI 门禁因此一直是红的（Linux Actions run 37420884434：host `+420 ~2 -2`）：
- 「an object without a binding falls back to the JSON page」：10 分钟超时；
- 「the helper returns null without a binding and disposes」：紧随其后报 `'!inTest': is not true`，是前一例超时后的**连带失败**，本身没问题。
- E11b 合入后，它新增的「the helper disposes the session when it returns null」也会连带失败（`Reentrant call to runAsync() denied`）。修好后整个文件 6 个用例应全部通过。

**根因（P0-S1 第 3 轮核实时插桩确认，测试问题，不是产品缺陷）：**
1. 无绑定的用例走回退路径：`openModuleObjectPage` 返回 null → `host.tools.resolveScope`（`platform_shell.dart:201`）→ `resolveAssistantScope` 中 `await host.activatePrototype()`（`business_tools.dart:129`）。这发生在点击触发的 **FakeAsync 区域**里，做了 3 次数据库写入。
2. 写入队列 `ManagedConnection.write` 用 `_tail = _tail.then(...)` 串接（`storage_manager.dart:27`），所以 `_tail` 这个 Future 属于假时间区域。
3. tearDown 在 `tester.runAsync(() => host.close())`（test:34-36）里经 `personalAgent.close()` 再写一次库，要挂在 `_tail` 上；完成回调被调度到假时间区域的微任务队列，`runAsync` 期间没人 pump，于是永远等下去。
4. 产品里只有一个区域，不会发生。

已验证的修法：在 `seed` 的 `runAsync` 里加一行 `await host.activatePrototype();`，让原型在真实时间里先激活，整个文件 5 个用例约 7 秒全部通过。

## 只做这些
- 只改 `apps/muyon/test/research_object_open_test.dart`，不改产品代码。
- 按上面的修法在 seed 中预先激活原型，并在旁边写一句注释说明原因（假时间区域里创建的写入队列会让 tearDown 的真实区域写入死锁）。
- 不能用加长超时、跳过、重试或 sleep。
- 提交并推送到本分支，不要合并 `develop`。
