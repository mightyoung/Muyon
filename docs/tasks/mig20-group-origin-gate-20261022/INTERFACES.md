## Source provenance and actual preparation

Owner schema4 adds `request_origins(request_id TEXT PRIMARY KEY,record TEXT NOT NULL)` in the SAME SQLite DB as requests/tool_steps. Every new first preparation inserts its actual request and immutable origin within one transaction. There is no public rewrite/reclassify-origin function. No request can be returned from group prepare as Direct and patched later.

- `AgentOwner::request_origin(&self,request:&str) -> owner::Result<owner::origin::RequestOrigin>`: opaque Serialize-only actual fact, private record; exposes `is_direct()`, `is_group()`, `root_request_id()`, `conversation_id()`. The read checks current actual stored canonical request/digest identity, classification/group consistency and actual reverse tool_steps links through up to32 ancestors. Missing/corrupt/duplicate/cyclic/contradictory source is an error, never a Direct fallback.
- `BusinessStore::group_prepare_chat(&self,group_scope:&GroupScope,owner:&AgentOwner,ledger:&RunLedger,workflow_scope:&RunScope,request:gate::GroupChatPreparation<'_>,verifier:Option<&dyn HostedCostVerifier>) -> contract::Result<AgentPlan>` is the native group prepare hook (7 parameters including self). Selectors are run_id, workflow_run_id, member_id and text. Workspace/project/group/root/conversation/actual member membership/coordinator epoch/group revision/current native epoch/session come from actual Store/RunLedger facts. Child must be current, enabled real remote_chat, queued and unbound, not cancelled; stopped/deadline group refuses. Real skill tool whitelist comes from existing ledger.remote_context, not client JSON. Standard proof/disclosure/prepare limits still apply. No reservation or permission is generated by the group identity.
- Group seed is crate-private, not a public FFI-deserializable constructor. The only added preparation entry calls the existing inner prepare encoder with the actual group seed and real restricted tool list. Existing ordinary chat/search/restricted prepare creates Direct origin in the same request transaction. Once group provenance exists in a conversation, ordinary prepare is refused before its first SQL write.
- Original ordinary Direct preparation does not establish absence of a group relationship: the read gate still checks actual persisted group/ledger evidence. A group child created through an old generic workflow path cannot use the Direct label to evade the new gate.

Origin record contains actual request/workspace/conversation/config/request epoch/canonical digest, classification `direct|group|legacy_unknown`, exact first original/root_request_id and parent_request_id, and optional group metadata: workspace/project/group/run/root_task/workflow_child/member/conversation, coordinator epoch/group revision/native owner epoch/host session.

Followup: the existing `prepare_tool_followup_trusted` remains the only tool followup writer. Its minimal callsite now passes exact parent request ID instead of conversation; origin/root are inherited from actual parent, with new parent ID. Full parent request17 columns/tool step8 columns/origin raw string are frozen BEFORE first new request INSERT, then compared at tail after request/link/parent-status writes. Child intended full request+origin is also read back. Parent status becomes tool_consumed and child is prepared only if the existing actual writer commits; origin failure rolls back the whole transaction. Missing legacy/parent proof refuses followup rather than laundering it into Direct.

Before any migration write, freeze original requests/configuration/tool_steps; after all writes and schema/version UPDATE triggers, compare whole ordered original tables byte-for-byte plus exact expected new origin rows and version4. Any change/injection/removal rolls back the FULL upgrade. Missing/partial origin table under version4 is an error, not automatic origin reconstruction.

Original status/charge/reservation/attempt/answer/tool records remain untouched. Existing lookup/chain/hold reads survive restart; unknown is never refunded, resent or called failed. Existing known new Direct nongroup requests, nongroup workflow children and first ordinary tool followup retain their original confirmation semantics in controls. ## Request-only read gate for the original FFI owner

- `RunLedger::request_attribution(&self,request:&str,owner:&AgentOwner) -> workflow::Result<Option<WorkflowRequestAttribution>>` derives selection from actual persisted conversation AND exact request/current/original-chain-root references, then reuses full admission facts, actual Owner chains, actual root/project/child/private session. It includes a real prepared but unbound child. It checks physical indexing before concluding no child; damaged conversation cannot erase a still-present request reference. No client RunScope, plan or JSON supplies attribution. The fact exposes facts(), child(), chain_contains_request() and Serialize only.
- `BusinessStore::group_request_gate(&self,request:&str,owner:&AgentOwner,ledger:&RunLedger) -> gate::GroupRequestGate`: always returns a typed Serialize-only observation; errors are captured as `group_hold=true`, `reason=source_inconclusive`, source_error. Public getter `group_hold()` is the sole new decision helper. It ALWAYS reports execution_authority=false and cross_owner_atomic=false.

It independently reads actual local group evidence before considering nongroup: registration conversation, actual node request reference, canonical mapping original ID, exact journal BindOriginal/BindCanonical request/root identities, pending missing source, and complete owned namespace remnants. Then actual root/project registration, Start records and current group runs are checked against reverse Ledger attribution. Missing run rows or mapping/metadata cannot prove nongroup. Group followups resolve mapping by their durable FIRST original, never look up only the newest followup ID. Mapping damage or no mapping remains HOLD; no auto-initialize, local replay, group re-register or new request occurs.

Stable current reasons:

|---|---|---|
| direct_non_group_observed | false | Actual new Direct source and no current group evidence after owner reads. Classification only; retain ALL existing auth/config/budget/gateway checks. |

| cross_owner_consumption_unclosed | true | Durable local mapping found; separate owner/gateway budget/attempt/claim consumption remains unclosed. |
| source_inconclusive | true | Missing/corrupt/inconsistent/read-failed source; no positive nongroup conclusion. |

Integration: before each existing agent_confirm, agent_claim and agent_allowed, call this gate with the actual Store/AgentOwner/RunLedger from the host state and exact request. HOLD or absent owner/ledger/error must refuse that action. Do not deserialize client/cache JSON into a gate, discard errors as None/Direct, or use a non-HOLD classification as a permit. Preserve the existing request authorizer, workspace/project/account checks, explicit confirmation, actual budget/attempt/epoch/configuration checks and sole claim_dispatch/allowed path. Only that owner may add bridge routing. Group preparation must route through the native group hook BEFORE any request is published, not call generic Direct prepare then associate later.

## Explicit remaining limitations

No group-wide budget/attempt/claim protocol or cross-SQLite atomic permission is closed here. Every group request therefore remains HOLD even when mapping/current facts look consistent. Publication, engine isolation and true provider execution HOLD are unchanged. There is no second dispatcher.
