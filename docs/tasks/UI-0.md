# UI-0 现状截图与走查

分支 `task/ui-0-baseline`（由 leader 从 `develop` 创建）· 执行 本地 engineer · 审查 leader · 依赖 无（只读，不改代码）

设计依据：[ui-redesign-brief-2026-10-06.md](../design/ui-redesign-brief-2026-10-06.md)。范围冻结期内允许（只截图、只写文档）。

## 目标
为 UI 重设计留一份**可复核的现状基线**，并核对设计稿 §2 的问题 D1–D9 是否属实、有无遗漏。设计稿的问题判断来自读代码，没有运行应用。

## 步骤
1. 环境：`bash scripts/doctor.sh`；用隔离数据目录运行，**不要用真实数据、不要填真实密钥**：
   `flutter run -d macos --dart-define=MUYON_DATA_DIR=/absolute/private/tmp/muyon-ui-baseline`
   有 Android 真机/模拟器时同样跑一遍；没有的平台写「未验证」。
2. 数据：用应用里现有的导入入口造最少的演示数据（一个工作区、一个研究项目、一份知识文档、一两个询价对象）。不能造的写明。
3. 截图矩阵。每一屏按「浅色 / 深色」× 宽度「320（或手机）/ 390 / 430 / 1280」截；桌面端用窗口缩放，手机端用模拟器。大字体（系统 200%）只对下列标 ★ 的屏幕各补一张。
   - 平台：工作台 ★、助手（含工具确认框、任务暂停/恢复）、资料、我的、个人中心、消息中心、执行面板、设备与通信、设备聊天（会话列表+对话）、记忆、系统设置 ★、数据与存储、数据去向、接口与工具、MCP 服务器、对象详情（知识文档、论文、询价对象各一）。
   - 询价（原 Folio）：每个 Section（工作台、项目、报价、供应商、物料、问数据、同步与交换、数据中心、设置、AI 任务、公司资料）的主页各一张；更多菜单（窄屏）一张。
   - 科研：概览、文库、任务、结果、写作各一张；阅读器、研究关系图各一张。
   - 原型：列表、版本评审、受限 WebView 各一张。
   - 空态/错态：至少各抓 3 个页面的「无数据」「失败」状态（模拟失败可用无模型、断开设备等现成条件，不改代码）。
4. 文件放 `docs/evidence/ui-baseline/<平台>/<屏幕>-<浅|深>-<宽度>.png`，并写 `docs/evidence/ui-baseline/README.md` 作为索引（表格：文件 · 屏幕 · 状态）。截图前确认画面里**没有真实密钥、真实路径中的用户名、私有地址**。
5. 走查报告 `docs/evidence/ui-baseline/walkthrough.md`：
   - 逐条判定设计稿 D1–D9：属实 / 部分属实 / 不属实，各附 1 张截图为证。
   - 记录设计稿**没发现的问题**（溢出、截断、点击区域过小、对比度、深色不一致、同一概念多种叫法等）。
   - 统计：从启动到完成下列 3 件事各需要几次点击、经过几个页面：① 向助手提问并确认一次工具调用；② 在设备页接纳一份来件；③ 打开一个询价项目并看到其预算。
   - 列出三套视觉的实际差异：平台壳、询价、科研（字号、圆角、颜色、间距、图标风格）。
6. 对照 Muse：参考截图含个人内容、不在仓库里：向用户索取，放在工作目录且不要提交；写一页「沐阳现状 vs Muse」的对照（底栏/导航、页头、列表、设置、空态），只记事实。

## 验收（leader 按 REVIEW.md「必做」+ 下列）
- 截图矩阵齐全，缺的有原因；索引与文件一一对应。
- D1–D9 每条都有判定和证据；没有「看起来」「应该」式结论。
- 没有密钥、真实路径用户名、私有地址（`grep -rn` 自查并贴命令与空输出）。
- **不改任何代码、不改 `develop` 上的文档**；不新增依赖。
- 报告里写明运行的平台、Flutter 版本、日期。

## 不做
不修 UI 问题，不改主题，不重命名。发现问题记入 walkthrough，由 UI-1 以后处理。
