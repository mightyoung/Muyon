Reading those SQLite tables alone cannot reconstruct authority, and object_catalog is explicitly untrusted candidate data. We will not invent a persistent read grant or second authority.

## Installed trust boundary and current authority

Trusted host installs an exact regular SQLite file path and one supplier ID. Installation freezes callback object ownership plus file dev/ino/uid/mode; every ancestor must be a directory without symlink, and file/ancestry identity is rechecked before/after each read and current-authority sample. Replacement or owner/mode change fails closed. No operation request supplies a path, SQL, grant, allow flag, or authority snapshot. Connection is READONLY, no URI interpretation or create, bounded queries/busy time. IDs are at most128 UTF-8 bytes; source payload at most65536 bytes, JSON object nesting/node/string bounds use existing contract parser validation; name is a string at most4096 UTF-8 bytes and2000 Unicode scalar values (no normalization). Unknown format/schema/required table shape, malformed JSON, unavailable file, missing/deleted record, invalid revision or oversized source/name fails closed. Open host-owned standalone copies only in this task; live production opening/locking/backup integration is a later gate.

A mandatory `Rc<dyn AuthoritySource>` is installed by trusted host code. Production implementation MUST delegate to existing ScopeResolver and host current policy/revision state, with UNKNOWN on pending/revoking/unavailable state; there is no permissive fallback. This task supplies a current-authority adapter that re-samples that callback, requires existing closed read-authority fields, allowed/available/scope_allowed, selected exact inquiry/supplier@1 ref, scope, binding/rule/source/authority revisions, and verifies selected record revision against the SQLite row. It forces model_allowed=false. Host callback is not implemented by a UI JSON DTO. Tests use a mutable trusted callback fixture; this does NOT prove production Dart/native bridging.

Authority is checked by the existing NativeSession before dispatch, immediately before handler entry, after read, and before projection acceptance. The handler also checks selected ref and revision under its read transaction. A fresh consumption call rereads SQLite and compares current/pinned row revision plus current host authority; it never returns a cached name. ## Registered read, receipt, separate business projection

New private closed operation inquiry/supplier_name@1, trusted binding host-supplier-name-read. Request is exactly {id:string}; the installed supplier identity must match. Projection is exactly {supplier:<inquiry/supplier@1 reference>,name:string}; the native version is rendered as decimal revision. Existing inquiry/object@1 and its reference-only projection remain unchanged. No projection/name is added to private Service current/lookup summary wire.

A local Rust UI/Service consumption facade creates the existing in-process NativeSession with this enrollment and dispatches the registered read synchronously, without model/provider/HTTP/reopen. It returns the accepted projection plus the ORIGINAL ToolRegistry receipt_ref from that same NativeSession. Existing receipt durable binding and current-authority gates are reused. Its source read connection cannot write business data; only the existing separate host receipt state directory is written. The receipt's success alone does not assert current data. Android Binder/JNI/Service/root wiring and actual UI consumption remain unimplemented and explicitly reported.
