# 原子批量写入执行契约（CR-6，ChatGPT 6 Pro）

状态：**设计稿，B1～B5 已由用户采纳（全部按推荐，见 ADR-0001 末尾 2026-10-11 条）** · 依据：`task/decisions-20261011b` @ `b521591`；GB-5 另读 `e12f3b3` · 只读静态设计 · 原稿由用户转交，leader A 整理入库，保留全部结论、契约、验收编号与待决事项，代码位置以原稿为准。已定边界（同模块同类型同操作同范围、50 条上限取更严者、外部内容只给逐项、ADR-0002 授权）不再讨论。

## 结论
新增复合写工具 **`inquiry.atomic_batch_write`**：一个冻结批次 = 一个业务 `operation_id` + 一次必要审批 + 一次工具调用 + 一个领域事务 + 一份整批业务回执。任一检查或写入失败全部回滚；结果不确定时保留原批次身份只读查核。
| 问题 | 结论 |
|---|---|
| 工具形态 | 新增固定原子语义的写工具；四个单条工具保留，共用单行校验与领域写入逻辑 |
| 一次批准覆盖 | 冻结的完整成员、逐行目标与版本、规范化变更、范围、契约版本；任何业务内容变化使旧批准失效 |
| 原子性覆盖 | **同一领域数据库**内的全部业务记录、变更日志、整批业务回执 |
| 宿主审批 | 与领域数据分库，经执行记录与恢复查核衔接，不宣称整条链共同提交 |
| 防重复 | 执行前持久绑定 `operation_id → batch_digest`；已提交返回原回执；同 ID 换内容一律拒绝（含首次失败后） |
| 取消 / 超时 | 只有已证实未开始或已回滚才说「整批未写入」；提交结果不明为「结果待核实」 |
| 回执未知 | 原 ID、原摘要、原执行身份只读查核；「没查到」还须旧调用已结束的证据 |
| 批内依赖 | 首版明确拒绝依赖批内先后的删除、恢复、新建关联，不做隐式级联或依赖调度 |
现有代码必须补的三点：现 `executeCard` 对选中操作逐条准备审批调用，前面成功的不回滚；恢复不能靠重放原写入口（单条工具先核当前版本再查回执，已提交更新改变版本会先被拒）；不能在事务回调里把错误转成普通返回值继续（`Store.transaction` 正常返回即提交，异常才回滚）。

## 1. 形态
- 注册：模块 `inquiry`、`ToolEffect.write`、宿主绑定的询价主领域库、宿主解析的显式选定范围、全部提交或全部回滚、每批只一种操作（create/update/delete/restore）、每行最多一个直接目标的业务变更。关联批量属于 `update`（提交源对象关系字段，`refList` 为完整最终列表）。报价沿用已定边界。
- 根参数：`contract_version`（首版 `atomic-batch/v1`）、`operation_id`（宿主冻结时生成的小写 UUID v4）、`type`、`operation`、`rows`（1～50）；模块、数据库、范围、审批证明来自宿主上下文。
- 逐行：都要稳定 `row_id`；create 带 `values`（不接受已有 `id`、伪造版本、临时引用）；update 带 `id`、`expected_version`、`values`（只含真实改动，空更新拒绝）；delete 带 `id`、`expected_version`、完整 `referencing_records`（有活跃引用仍拒）；restore 带 `id`、`expected_version`（不夹带字段修改）。宿主私有记录另存逐行基线摘要、完整差异、依赖证明、草稿修订。
- 三种身份分开：`row_id`（草稿行与结果行对应）、对象业务 ID（含新建后的真实 ID，回执保存 `row_id → 新 ID` 映射）、`operation_id`（整批幂等）。新建行不能引用本批另一待新建行。
- 「同范围」= 同一宿主冻结执行范围 + 同一领域库实例 + 同一写入归属，所有目标与依赖经宿主解析核对；项目内目标不得借批量移到别的项目；新建对象不自动获得后续写权限。重复：`row_id` 重复或更新 / 删除 / 恢复里同一对象重复 → 整批拒绝；新建按领域规则，不按名称去重、不静默丢行。
- 结果：`committed`（每行 applied）、`not_committed`（每行 not_applied）、`unknown`（每行 unknown，保持执行锁）；**不允许部分成功**。成功回执含回执版本、`operation_id`、`batch_digest`、模块、工具、领域库身份、类型、操作、范围摘要、提交时间、行数、逐行 `row_id` / 真实 ID / 提交后版本 / 删除状态 / `ObjectRef`、可恢复的变更清单与新建 ID 映射。失败诊断：稳定错误码、失败阶段、`row_id`、字段路径、经读权限检查的当前版本；冲突仍是 `failed + 结构化 data`。**现 `ToolCallResult.changes` 不进 `toJson()`**，整批回执须显式序列化变更清单。
- 复用：共享参数与白名单检查、单行候选准备（基线、版本、规范化、范围与引用、完整领域检查）、单行应用（保存 / 删除 / 恢复与日志）；单条工具与复合工具各自组织事务与回执。不能循环调用原 handler（它同时负责激活、范围复核、单行回执、写入、通知，前一行改版本会让下一轮复核失败）；共享校验不能只抽 `_validateArguments`，`Store.save` 的报价、预算行、价格口径、单位换算、引用规则都要保留。

## 2. 授权
- 顺序：宿主确定资格 → 插件规范化与完整只读校验 → 宿主生成逐行真实差异 → 冻结批次 → 取得批准。执行时规范化结果与已确认不同 → 退回重新确认。
- `batch_digest`（「是不是同一个业务批次」）：SHA-256 over 版本化规范 JSON 的 UTF-8；包含契约版本、工具、模块、领域库身份、`operation_id`、类型、操作、原范围身份、目标与依赖的版本 / 内容证明、完整执行行（`row_id`、目标、预期版本、规范化变更、删除引用预览）、影响写入解释的本体 / 可写声明 / 校验规则版本。规则：键递归排序；行按 `row_id` 排序；普通数组保序，只有声明为集合的字段才集合规范化；精确十进制保留字符串；区分未提供、`null`、空串、零、false、空列表；不含 UI 展开 / 滚动 / 分页 / 显示排序。
- 审批身份（「这次调用现在是否获准」）：沿用并扩展现 `identity_digest`，另绑 `invocationId`、`replayKey`、任务 / 卡片 / 草稿修订、范围修订、工具注册代次与可用性、污染事实与来源修订、授权 / 策略状态、批准有效期；这些**不进** `batch_digest`，否则同内容重新批准会被误判为换内容。
- 失效：增删排除重选行、改目标 / 版本 / 值 / 引用 / 删除预览、修改未解析的输入缓冲、范围 / 模块绑定 / 声明版本变化、污染变 tainted 或 unknown、授权撤销过期或工具不可用 → 旧确认与旧回调失效；业务内容改变用新 `operation_id`；旧批次已派发且结果未知时必须先查核，不能改草稿换 ID 绕过锁。纯视图变化不失效。
- 与已有授权：默认询问；复合工具不继承单条工具授权；用户对**该复合工具、该范围**有有效授权时由宿主按 ADR-0002 判定是否代签本批一次性批准；一次批次调用消耗一次批准；不新增持久授权入口；查阅历史回执是只读，不消耗写入批准。
- 外部内容：`tainted`、`unknown`、污染记录缺失或损坏都不能进原子批量；在呈现、派发、签发、执行边界分别检查；只有真实单项入口可用时才转逐项（每项独立 ID、确认、回执，保留「仅这一次 / 拒绝」，无整批放行，明示前项成功不随后项失败回滚，污染继承）。现动态接线 `onIndividual` 为 `null`，不能声称逐项入口已完成。

## 3. 执行
- 原子边界：批内全部目标记录变更、领域日志、整批成功回执在**同一物理领域库、同一最外层事务**共同提交或回滚。宿主 `muyon` 库与询价 `inquiry` 库分开（询价另有 jobs、hub 库），同模块不等于同事务域；审批消费、执行状态、对话保存、通知不在原子承诺内；事务内不夹带网络、文件、另一个库或外部工具效果。
- 步骤：(1) 冻结与登记（持久保存不可变批次与 ID→摘要绑定，完成批准）；(2) 排队与复核（激活模块，取得该批次唯一活动执行资格，异步等待后重读宿主事实）；(3) 由批量入口控制唯一最外层事务，后续领域操作同步；(4) **在重查旧对象版本之前**按 ID、摘要、领域身份查既有批回执，匹配走历史结果，冲突拒绝；(5) 基于事务初始状态检查全部目标、版本、摘要、删除状态、范围、规范化、引用、领域规则；(6) 检查整批计划（重复对象、批内相互影响、最终唯一性），不能证明合法则整批拒绝；(7) 复核资格后应用全部行、写日志、构造并校验完整回执写入同一事务；(8) 最终提交门：复核取消、期限、授权、污染、执行代次后提交；(9) 最外层确认提交后才发布成功、更新宿主回执与卡片。第 5、6 步在第一条业务变更前完成；最后的宿主检查不得把本批自身写入导致的版本变化当成外部变化。
- 错误传播：任何行、日志、回执、序列化、提交前检查失败都以能中止最外层事务的异常传播，事务外才转成工具错误；禁止捕获后继续写、返回普通失败对象让外层提交、内层返回即发布成功、提交前发通知。嵌套 `Store.transaction` 只加入外层，无保存点。
- 首版批内依赖：删除只要事务开始时存在活跃引用就拒（含本批其他待删对象的引用）；恢复的被引用对象须事务开始时已存活；新建只引用已有且通过检查的对象；需要依赖执行顺序或扩大写集合才能完成的更新拒绝；不隐式追加、不自动跳过失败行。
- 取消与超时：事务前确认取消 → 未写入；事务内最终提交门前接受的取消、失权、超预算 → 回滚；越过提交门结果未明 → 「取消已收到、结果待核实」；已提交 → 保留成功，后到取消不改写；回滚或提交出错 → `unknown`。最终提交门须保证资格核验到 COMMIT 之间不插入已被宿主接受却未参与判断的撤销（首版在同一宿主执行协调范围内串行）。同步事务是协作取消；`Future` 超时、页面关闭、网络断开不构成回滚证明；Registry 在效果开始后遇取消返回 `interrupted` 的保守边界保留。
- 幂等两层：宿主不可变意图绑定（执行前保存，失败取消后也不删）+ 领域提交证明（与业务变更同事务）。同 ID 同摘要已有成功回执 → 返回原历史结果（不重新生成新建 ID）；同 ID 不同摘要 → `operation_id_conflict`（含原尝试失败或取消后）；同 ID 同摘要旧调用仍在执行 → 关联或返回处理中；旧结果未知 → 查核，不启新尝试；已证实旧尝试结束且未提交、用户要求重试 → 保持业务 ID 与内容，重新取得批准，新调用身份；改内容 → 新批次身份（前批未知时不得借此重发）。

## 4. 恢复
- 经 GB-5 提议的业务回执能力做宿主受控只读查核，不把再次调用写工具当恢复。查询带模块、工具、领域库身份、原 `operation_id`、`batch_digest`、原范围身份与当前读取资格；**验证当前读取权限，但不要求目标仍处写入前版本**；读取资格不足拒绝披露，不返回「未执行」。
- 判定：完整回执匹配 → 整批已提交（返回提交时历史版本与 ID 映射）；同 ID 但摘要或身份不同 → 冲突；未查到且旧调用可能仍在运行或等锁 → 仍未知；未查到且旧调用已退出或已证实回滚、库恢复完成、无其他在途尝试 → 确认未提交；模块不可用、存储错误、权限拒绝、回执损坏 → 不可完成，不当未提交；只有宿主 `failed` 标签、无可信未执行或回滚证明 → 继续查核。时间过去、租约到期、等待超时 ≠ 旧调用已结束，首版不按时间强行接管。
- 领域已提交而宿主终态未落盘的窗口（现调用链：宿主库消费批准并登记 running → handler → 另写宿主终态）：以匹配的领域回执为准，宿主补记「已查核」结果并保留原轨迹，卡片、索引、投影按原 ID 幂等更新，不触发下一次写，不扩大授权，污染继承。
- 生命周期：常规对话清理不删防重与恢复证据；完整批回执保留，后续清理至少留不可重执行的提交标记、摘要、身份；明细不可恢复时明说，不生成新 ID 重做。

## 5. 宿主与模块边界、与 GB-5 衔接
- 宿主：身份、注册与调用入口、范围权限污染、批次冻结摘要与 ID 绑定、一次性批准与撤销、执行协调与最终提交资格、宿主回执与卡片状态、恢复调度。模块：支持哪些类型与操作、可写字段与规范化、领域检查、整批候选与相互约束检查、单一领域事务内应用、同事务回执与日志、只读提供领域回执。模块不能经参数、`scopeProof` 或模型 JSON 自授权限。
- `muyon_module_api` 拟增量：写表单操作声明加可选 `AtomicBatchSpec`（缺省不支持）；批量能力声明（复合工具 ID、事务域、最大行数、字节预算、依赖策略，宿主核对与实际注册一致）；`validateBatchDraft`（规范化行、行错误、批次级错误、草稿修订、依赖证明）；独立原子批量特征标记；版本化整批结果；结构化回执查询对象；宿主控制的事务提交资格复核。执行仍经现 Registry 的注册工具。现 `ModuleFeature` 只有五项、`WriteToolSpec` 无原子性声明，均非现成接口。
- 对 GB-5 的对齐要求：可写声明额外标明是否支持原子批量（不能从单条可写推导）；`validateDraft` 补批次级检查；`WriteConflict` 增 `row_id`、失败阶段与整批未提交证明；`lookupBusinessReceipt(String operationId)` 参数不足，须绑原摘要、工具、范围、领域身份；成功回执身份与摘要必须完整，查不到 / 冲突 / 不可读 / 结果未知须可区分；`scopeProof`、`dependencyProof` 须明确发行者、草稿修订与摘要绑定，由宿主验证。CR-2 D1～D11 已由用户决定，不再待决。

## 6. 上限与预算（50 条已定，其余为待实测初值）
行数 1～50 取最严；整批原始与规范化输入 ≤ 256 KiB；单行规范化参数 ≤ 16 KiB；依赖与引用证明 ≤ 500 个不同对象（计入整批预算）；单条工具字段限制保留不放宽；排队预算约 5 秒（到期重核，不自动另派）；事务协作截止约 2 秒（检查点与提交门核验，不是硬中断，COMMIT 晚返回仍按真实结果判定）；整批回执 ≤ 256 KiB。确认卡：固定显示执行数、排除数、类型、操作、范围与「任一失败整批不保存」；全部选中行完整差异可访问，分页过滤后仍显示全批选中数；错误、缺失必填、本次修改字段不可折叠隐藏；敏感字段默认遮盖、显露不外发；超预算或无法完整呈现即停止提交并提示拆批，不截取前 50 条、不静默拆批；拆批后每批独立确认独立事务。

## 7. 验收（AB-01～AB-34，未执行）
- 准入与授权：AB-01 混模块 / 类型 / 操作 / 范围 / 领域库整批拒绝零变更；AB-02 0 行、51 行或超任一预算拒绝不截断不拆批；AB-03 `row_id` 或目标对象重复拒绝；AB-04 未知 / 保护 / 不允许字段、非法版本、空更新在提交前与执行边界都拒绝；AB-05 模型伪造工具、范围、批准、ID、依赖证明不作依据；AB-06 确认后改行、成员、版本、非法缓冲 → 旧批准与回调失效；AB-07 纯视图变化不改执行集合与摘要；AB-08 单条工具授权不迁移给复合工具；AB-09 排队后授权撤销 / 过期 / 工具撤回 / 范围变化 → 执行前拒或整体回滚；AB-10 外部内容、污染未知或确认后变污染 → 原子批量拒绝、无整批放行；AB-11 逐项入口未接线时不展示为可用。
