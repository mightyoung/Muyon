# B3 宿主确定性风险分级规格（B3-RISK-SPEC，ChatGPT）

基线 develop `9de4235a`。只读规格，未改代码、未跑测试。原稿由用户转交（含 31 条验收用例 RT-01～31、18 个实施任务），leader A 整理入库，代码位置以原稿为准。设计思路参考业界做法，不含任何第三方提示词或代码。

**结论：** 六档风险 R0～R5，由宿主按可核实的操作事实确定性计算（不调用模型）。R1、普通 R2 在现有授权规则下可自动；**R3、R4 必须逐次人工**；R5 直接拒绝。`NoopReviewer` 保留「未做内容审查、审查层不额外阻断」语义；另设不可绕过的宿主风险门——高风险是否必须人工与有无审查器无关，真实审查器 allow 也不能替代本次人工批准。

## 1. 六档
| 等级 | 定义 | 判定（取最严，不加权） | 例 |
|---|---|---|---|
| R0 受控只读 | 无业务写入、文件生成、外传 | 已验收只读能力，范围合法，无隐藏子效果 | N2 预览、查询、回执读取 |
| R1 可恢复单条本机写 | 一个目标的受控变更 | 实际变更目标恰为 1、无级联、无外传，且**有真实领域恢复实现并与写入共同保存完整恢复凭据** | 可恢复的单字段修改 |
| R2 受控内容处理与传输 | 内容与接收方均明确 | 宿主控制实际载荷与目标，过披露与目的地规则，无远端业务变更 / 发布 / 发消息 / 设备动作 | 普通模型请求、受控检索、CR-17 新建导出副本 |
| R3 高影响本机写 | 不可恢复、批量、级联或破坏性覆盖 | 明确不可恢复；或影响已知但不能证明恢复；或实际变更目标 ≥2；或级联删除；或批量能力（即使本次 1 行） | 删除段落及关联、原子批量、覆盖 |
| R4 高影响外部效果 | 对外部系统产生业务效果 | 远端 create/update/delete、publish、sendMessage、deviceCommand 或含其子效果 | 外部写 API、发送给收件人 |
| R5 明确禁止 | 硬规则不允许 | 越能力、禁止目的地、禁止披露、CR-6 超限或污染批次、伪造目标能力 | 51 条原子批 |
要点：事务可回滚 ≠ 可恢复；模块声明 `reversible` / `count` / `risk` / `manual` 都不能直接作授权证据；原子性不降低批量风险；授权不改风险（管理员 never 拒 R0 记为「R0 + 政策拒绝」）。
可信事实：模块可提供候选，宿主核实受信 profile、实际目标、完整影响集合与计数、恢复实现、实际端点 / 字节 / 来源、污染与政策。首版低风险资格只授予宿主验收过、效果边界受控的能力。
未知：恢复未知但影响已核实 → R3 可人工；目标 / 级联 / 目的地不可核实 → 不执行、不提供盲签；已开始效果结果未知 → 只读核验，不重发。
批准绑定事实而非等级：在现有 `identityDigest` 上加入风险事实摘要、风险规则版本、确认预览摘要（2 条与 500 条同为 R3 也不能共用批准）。

## 2. 风险 × 授权
| 风险 | 无授权 | 预授 once | 会话 / 任务 / 限时 / 长期 grant | 本次知情人工批准 |
|---|---|---|---|---|
| R0 | 依读取政策 | 不用 grant | 不用 grant | 管理员 ask 时需要 |
| R1 | 询问 | 可自动 | 可自动 | 允许 |
| R2 | 询问（模型 `mode_auto` 为限定例外） | 通常可自动 | 合法授权下可自动；outbound 不接受 always | 允许；CR-17 分阶段 |
| R3 | 逐次询问 | **不得代签** | **不得代签** | 允许本次冻结动作 / 完整批次 |
| R4 | 逐次询问 | **不得代签** | **不得代签** | 允许本次 |
| R5 | 拒绝 | 拒绝 | 拒绝 | **仍拒绝** |
覆盖约束：管理员 never / 类别关闭 / 硬禁止 / 审查 block → 拒绝；管理员 ask / 审查 confirm 或异常 → 本次人工；新远程端点首次人工；write/outbound 污染不匹配 grant（model 例外保留）；CR-6 原子批遇污染整批拒绝；CR-17 A、B 各需本次人工；拒绝记忆命中阻止自动执行与自动重开卡；风险准备不完整或已有未知效果不签发。
人工批准须是宿主不可伪造的能力：绑定用户、会话、活跃卡、最终调用身份、风险事实、预览、政策版本、有效期、一次性消费、导出阶段与目标。`manual=true` 字段或调用 `approve` 本身不算。R3/R4 卡只给「确认本次 / 拒绝」。

## 3. NoopReviewer
现状：`allow(reviewed:false)` = 未审查、不额外阻断；有有效 grant 时形成最终 allow，所以「默认 allow 不等于授权」成立，但「对自动执行无影响」不成立。生产链固定含 Noop 再追加可选 reviewer，链的 `reviewed` 取 AND，不能用 `reviewed=false` 判断「没装审查器」。
推荐：所有 R3/R4 必须人工；reviewer 只能收紧；风险门覆盖底层签发与效果执行，含无 `effectIntent` 的旧分支（`agent_dispatch.dart:325-337`、`tool_registry.dart:693-727`）。影响面：ADR-0002 增加高风险例外；CR-6 复合 grant 收紧为整批本次人工；现有无真实恢复能力的单条自动写升 R3；待确认卡 / 已签未执行批准 / 缓存 review 升级后失效重准备；历史回执兼容读取；未知锁保留；模型 `mode_auto` 与 model grant 保留。

## 4. 管理员天花板
做最小三态宿主政策（never 禁止、ask 本次人工、always = 「按用户授权规则」不额外收紧且不能使 R3/R4 自动），匹配类别 / 工具 / 范围 / 目的地，取最严，子范围不放宽父范围，覆盖 R0 与 `mode_auto`；无政策用默认上限，损坏闭锁；管理权须来自可信宿主所有者或独立管理源；修改立即使在途批准失效（A→B→A 不复活）。完整组织 RBAC 另立。

## 5. 衔接
- **N2**：预览 R0 → 同一快照取段落、全部关联、计数、`deleteDigest` → 删除 R3（500 关联 + 1 段落 = 501 个业务记录，受限关联也计数）→ 人工批准绑定快照 → 现有 `delete_section(expected_digest)` 事务 CAS；原生 `store.deleteSection` 入口收口。
- **CR-17**：准备 R0；A 生成通常 R2、本次人工；目标未知不预签 B；B 保存通常 R2、覆盖最低 R3；批准还须绑定 manifest、纳入 / 排除、计数、警示（现 intent 摘要未全含）；Android 空文档清理须证明本次创建。
- **CR-6**：所有原子批量最低 R3、整批本次人工；50 上限与污染禁令保留，不截断不拆批；业务 `batch_digest` 与批准身份分离；不得把本批自身写入导致的版本变化当过期。验收分「CR-6 v1 的 500 条 → 拒绝」与「合法支持 500 条的测试能力 + 会话 grant + Noop → 停在人工」两场景。
- **B4 拒绝记忆**：`conversationId + identityDigest`，由真实显式拒绝事件写入；先于 grant 自动签发；关闭页面 / 超时 / 另存为取消 / 审查 block 不算用户拒绝。因 `identityDigest` 含 invocationId，换 ID 可绕过 → 增加宿主辅助 `refusalFingerprint`（规范化业务动作、目标、范围、内容、目的地、后果，排除调用 nonce 与再生行 ID，保留重复行计数），只作负向阻止，不替代正式身份。先冻结风险与身份再查拒绝，避免摘要循环。
- 未知效果：N2、CR-17、CR-6 都以宿主持有的逻辑操作与尝试谱系维持未知锁，不能用新 `operation_id` 规避；历史 / 未知查询走只读分支。
