## 二 已确认的设计边界

以下作为本轮评审约束，评审不重新表决或静默改写：

1. 桌面 Electron，Android Kotlin Compose，共享 Rust 本机离线内核；不同设备各持自己的存储与执行账本，不自动共享任务、审批或数据
2. 生成卡的本地交互即时处理；参数明确的确定性业务动作直接进入 Rust 校验并执行；语义理解、生成新内容或重规划才需要模型
3. Auto 是独立档位，按可信规则区分低风险自动、高风险确认和禁止动作
4. FullAllow 在用户已选工作区和现有访问权限内免额外风险询问，包含高风险及此前未使用的新网站/API目的地；不得借 taint、内容复核不可用或换名“安全确认”恢复额外询问
5. 现有访问权、明确禁外发、撤权、稳定意图、对象版本和真实回执仍须校验；产品内 FullAllow 不授权本次评审自行进行真实外发、安装、账号操作或代码合并

若发现这些决定与某个技术设计或旧合同冲突，应写清冲突和后果，优先给出保留决定的兼容方案。确实需要改变产品决定时，单列为建议及取舍，不能先按相反决定给出“已修正”的结论。

**尚未决定：** 其他候选模式、默认档位和授权期限、旧配置完整映射；Android屏幕/设备内容读取范围；临时会话及其留存语义；记忆容量和保留策略；账号默认范围及是否仅限个人账号。不得从竞品行为或旧研究报告推导这些已经决定。`content_review` 的可信理由类型及旧 reviewer 映射属于待冻结合同，不能用它重开已定 FullAllow 语义。

## 三 必须给出的四个判断

## 五 评审输出格式

先用不超过十行给出四项判断、最重要的阻断和下一步。然后输出证据表与具体补丁建议，不只给笼统建议或重述设计。

每条新发现用 `V13-B01`、`V13-I01`、`V13-S01` 等编号，避免与旧评审编号冲突：

- **B 阻断**：明确阻断哪一关、哪项能力；给最小反例或无法实施的依赖证明
- **I 重要非阻断**：说明可继续范围、必须在哪个交付前补齐
- **S 建议**：说明改进收益和是否影响现有合同，不能当作强制范围扩张

每条必须包含：

1. 结论与影响范围，标明文档问题、源码事实、推断或待验证假设
2. 准确证据：完整SHA＋仓库路径＋行号/符号；文档用本轮MD章节和行号，图示用实际文件路径和图号
3. 两册相关位置和旧合同冲突位置；没有发现源码证据就直说，不能用“应当如此”作已实现事实
4. 最小修正及兼容方案，保留已确认决定；必要时写可直接替换的条款
5. 验收方法、前置、责任角色和关闭标准；未运行的测试/模型/设备/故障场景一律标“未验证”

最后附：旧评审逐项处理表、文档切换清单、首批任务依赖/停止条件，以及剩余产品决定及各自影响范围。若没有确定的 DOCS-G0 阻断，明确写“未发现阻断目标文档采纳的问题”，并保留能力开放的未验项，不用“全部通过”概括。
