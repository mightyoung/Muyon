## Minimal candidate interface (private proposal, needs parent/native contract)

Keep existing RustUiPort NOT_CONNECTED and diagnostic API backward-compatible. Add a distinct `AgentReadUiPort`/state holder for this narrow offline run; do not add generic CONNECTED or turn on “发送”. The first UI entry can be a sibling Settings “离线 Agent 读取实验” panel, showing actual Rust Agent runtime outcome and measured run counters over offline synthetic data, separate from the existing declaration diagnostic. It does not display business values. A broader assistant conversation integration is a subsequent contract because user prompts/model/retention are not present in this slice.

Suggested UI control shape (names provisional; not generated ABI):

```
attach(listener: (AgentReadSnapshot) -> Unit): ReadLease
submit(lease: ReadLease, variant: BundledReadVariant): LocalAdmission
stopObserving(lease: ReadLease, token: ReadToken)
detach(lease: ReadLease)
```

`LocalAdmission = AcceptedLocally(token) | Busy | Detached | Unavailable`. AcceptedLocally means the process coordinator reserved work, not that Rust accepted a task or performed a read. Snapshot separates `runtimeAvailability`, `nativeBusy`, local observation state and **Rust-returned** terminal outcome. No local boolean `succeeded`, no cancellation ACK, no local computation of authorization or policy status. Request token carries internal requestId plus lease generation; native result additionally correlates native build/runtime identity and actual Rust taskId/attemptId, variant, protocol. UI generation is equality-only presentation identity, not scope/authority version or a durable event cursor.

Smallest native adapter seam is a synchronous bounded `runRegisteredRead(request): ReadRunResult` invoked off-main through this coordinator. Request contains a private protocol/internal `[A-Za-z0-9_-]{1,64}` requestId and one fixed bundled case/variant. It accepts no user draft, arbitrary prompt, path, tool name/arguments, handler JSON, allowed/approved/tainted/classified booleans, grants, revision override, mode or model endpoint. Trusted bootstrap alone installs synthetic physical store, exact scope refs/bindings, read authority, purpose policy, handler and offline provider. Rust calls the existing Agent::run_with_runtime_ports and retains the existing full admission/order/budget/ledger/source-fact barriers.

Return only closed typed metadata: protocol/request correlation/build identity, actual Rust taskId/attemptId and terminal code, opaque original read-receipt identity/outcome, and bounded measured steps/calls/read-handler-entry counts. Export **no UI projection, business value, raw result, model history, serialized store or unchecked JSON**. UI can show “离线合成 Agent 运行” and actual terminal metadata; it does not claim product read permission or populate a chat response. Actual strict projection → second provider payload stays inside Rust and is verified by separate off-shipping Rust/Linux/JVM probes. No Kotlin-generated result or constant counter can replace that chain. A future requirement to display values needs a separately frozen Rust-owned UI-purpose/current-scope projection contract and is explicitly outside this slice.

Measured counter units must be frozen precisely: Agent counters.steps/calls are budget-charged step/provider-call attempts (A/src/agent.rs:225), not successful model/network calls; NativeSession.handler_calls increments immediately before ReadHandler.read (H/src/lib.rs:402), so it measures handler entry, not successful file reads/records. ## Runtime ownership and close semantics: two concrete choices

**Recommended first slice: bounded one-shot run.** Construct/use/drop all Rc session/provider/runtime state on one Rust-owned execution thread; FFI carries Send DTO/control only. A smaller equivalent can keep every non-Send value entirely on one synchronous FFI call stack on a fixed application worker, if nativeowner explicitly chooses/proves that lifetime. No object/Rc crosses FFI, no session survives function return. Function return is promised only after the actual Agent terminal is recorded and required owned child/worker cleanup is settled; unresolved cleanup is not Closed. UI Application owns the one request coordinator for the process. It must not have a panel/ViewModel-owned executor or shut it down on Activity disposal.

Panel close, stop-waiting and display timeout invalidate that lease only. Runtime busy remains until real run **and required cleanup** finish, including after panel/Activity recreation; no queue/retry/new worker. Rust persists historical receipt/source facts regardless of whether a live UI lease can consume the result. New holder cannot publish a stale terminal as a different request or automatically replay it. No business body is returned/cached in this slice; later real-data display would need its own Rust-owned admission. Do not delete private store files/receipts during detach or worker cancellation.

Parent-converged candidate includes independent native request_cancel/close; the earlier no-cancel alternative is no longer the recommended plan. Display-only “停止等待展示” remains a separate operation, with finite Rust/provider/transport budgets and no fake Cancelled terminal. An independent Rust-owned request-specific control flag/handle must be reachable while run is blocked; cancellation cannot be queued on the same blocked execution thread. Native worker/control checkpoints must actually observe it. Requesting cancel gives CancelRequested only; actual Rust terminal and original read/evidence outcome may differ. Close acknowledgment must reflect actual worker termination/resource cleanup, never merely a Kotlin Job.finally or a requested flag.

**Larger alternative: persistent runtime handle + submit/poll/control/close.** Requires Rust-owned Send facade/queue/worker around non-Send session, request-specific control, bounded pending work, runtime generation and real closed/join semantics. Poll does not run Agent again; timeout is not close/cancel. A new holder shares runtime; close permanently rejects new submit and is idempotent, but acknowledges Closed only when actually stopped/joined. This adds object finalizer/lifetime/JNA/FFI concurrency requirements absent from the stateless bridge. Do not take this larger scope without parent selecting it.

Diagnostic work and runtime work share one Application/process admission gate: diagnostic handshake/validation versus Agent run mutually return Busy while the other owns it. Preserve existing diagnostic API behavior and keep request presentation separate. Two independent coordinators with unrelated slots would violate this decision. Independent Rust cancellation/close control must bypass the *work* gate, use only the Rust-owned concurrent control primitive, and never acquire/mutate Rc session state from the control caller.

## Final parent-converged recommendation (supersedes projection alternatives)

After nativeowner and root independent-review alignment, the selected smaller first-slice candidate is: **open → one-shot run_once, with separate independent request_cancel/close control; no persistent task queue and no shipping UI projection.** This remains a proposal awaiting the exact root contract, not authorization to begin implementation. - Shipping exports actual typed task/attempt/terminal + opaque original receipt identity/outcome + bounded measured steps/provider-call/read-handler-entry counters. No raw/history/business value. A request cannot be acknowledged cancelled from a UI timeout or accepted control bit.

Cancel/close before native registration returning UnknownRun/NotAccepted cannot be taken as stopped, cannot release the slot, and cannot allow a pending queued run to start unnoticed. Prefer open establishes a real correlated control handle before run_once can execute; no automatic retry or manufactured acknowledgment.
