## Options and recommendation

1. **Recommended: existing nativehost with internal in-process transport and one Rust-owned worker.** Add only a private transport interface around current request/close dependency; keep current PluginProcess adapter for Linux/regression. A second adapter owns one persistent Catalog for the entire session and uses the same bounded envelopes. Same NativeSession/RuntimePorts/ModelGateway/physical handler/store/Agent drive execute. Non-Send objects are constructed, used and dropped inside the worker; only Send/Sync control records cross FFI. This follows already documented direction. It proves host-installed trusted Rust handlers, not arbitrary plugin code isolation.
2. **Keep child transport on Android.** Minimal Linux code change but requires executable packaging/path/exec/lifecycle/SELinux and kill/reap evidence not supplied by current.so/API24 lane. Compile might succeed while exec fails; feasibility remains unproved. Not recommended for smallest Android-feasible slice. Keep as Linux differential baseline, not quietly bypassed Android failure.
3. **Make all runtime state Send/Sync or add a service/process framework first.** Broad changes to authority/handlers/Rc/store/lifecycle and locking, extra deadlock/cancellation risks, no benefit for one bounded run. Defer. Returning UI business projections is a separate optional extension requiring explicit ui_display/current-scope-purpose policy; omit it now.

Do not simply call Catalog::handle or create a fresh Catalog per request. main.rs:5,14–25 owns oneCatalog and terminates after malformed JSON, incomplete/oversize frame, protocol_envelope/protocol_version/unsupported_command/unexpected_or_missing_field errors. Catalog::handle alone does not latch these. Catalog.inspect/close run before closed check (lib.rs:40–42); request(command=close) does **not** itself make main exit. A transport's explicit close()/EOF is distinct from that command. Freeze a child-vs-inprocess transcript corpus, including these differences, before choosing terminal normalization. Recommended private seam `request(Json)->Result<Json>; close()` encodes/parses both input/output with existing limits and latches the same fatal replies; explicit transport close permanently rejects future requests and drops tickets/Catalog. Preserve actual child semantics; no claim in-process has pipe EOF, process isolation or OS reaping.

## Minimum deliverable and exact candidate private DTO

This is a proposed private slice contract, not an approved M03/public interface. Root can rename/freeze it in the spec. Existing diagnostic API/availability stays separate. The scope is an **actual offline synthetic-data Agent run**, not metadata validation and not production business/model access.

Shipping API candidate:

```
open_read_runtime(RuntimeConfig { protocol:u32, private_root:String }) -> Result<Arc<ReadRuntime>, SetupError>
ReadRuntime.run_once(ReadRequest { protocol:u32, request_id:String, variant:ReadVariant }) -> Result<ReadRunReport, AdmissionError>
ReadRuntime.request_cancel(request_id:String) -> Result<CancelAck, ControlError>
ReadRuntime.close() -> CloseAck
ReadVariant = Equipment | Research | Inquiry | SeededEquipment
CancelAck = Requested | AlreadyTerminal | NotRunning
CloseAck = Closing | Closed
ReadRunReport {
 protocol:u32, request_id:String, build_identity:String,
 task_id:String, attempt_id:String,
 terminal: Completed | Cancelled | Failed | BudgetExhausted | OutcomeUnknown,
 reason: None | Cancelled | AuthorityDenied | PurposeDenied | ContractRejected |
         StorageFailure | ProviderFailure | DeadlineExceeded | BudgetExceeded |
         Interrupted | InternalFailure,
 receipt: OriginalReceiptSummary { opaque_id:Option<String>,
   outcome: NotStarted | RunningUnknown | RecordedSuccess | RecordedFailure }
}
```

Only enum tags and opaque identities are exposed. No projection, raw, answer, model_history, task context, filesystem path, authority snapshot or source facts in shipping result. No permission/grant/receipt counts or invented measurements. Real values/projection remain inside existing Rust chain and are independently checked through off-by-default test-only probes. UI can show actual task/attempt/terminal and synthetic/offline scope; operational send/model/business controls stay disabled. This avoids a new ui_display policy entirely. Receipt outcome and run terminal are separate facts: cancelling after durable raw success may be Cancelled + RecordedSuccess; cancellation is not rollback. A durable running/ambiguous receipt dominates final classification as OutcomeUnknown even if cancel/close requested. No opaque identity means no durable begin only when confirmed from authoritative state, never inferred from missing/unreadable evidence.

Closed setup/admission errors: UnsupportedProtocol, InvalidRequestId, InvalidRoot, Busy, Closed, RecoveryRequired, InternalFailure. Control errors: InvalidRequestId, RequestMismatch, Closed, InternalFailure; no protocol field is added to these control calls. No raw reason/stack/OS path in public errors. Once admitted, all ordinary failures become typed reports derived from actual persisted receipt/task facts; not just existing native_host_refused text. A panic/join failure that prevents certainty produces OutcomeUnknown/Interrupted and preserves evidence. Final classification must not use a cancel request as proof cancellation reached execution.

Input protocol1; request_id `[A-Za-z0-9_-]{1,64}`, generated by trusted caller, never path/authority. Variant chooses only four Rust-owned installed synthetic declarations (seed0x7631). No free-form provider response, declaration, path, grants, record payload, policy or model endpoint supplied by Kotlin. Task/attempt identities are generated by actual State::runtime, bounded by existing identifier rules; opaque receipt identity<=128bytes. Correlation/build mismatch is unavailable, not success.

## Ownership, storage and lifecycle bounds

Recommended scope: use app bootstrap's context.filesDir.canonicalFile as the trusted platform root, with Rust-owned namespace `native-agent-v1`. This supplies necessary durable NativeStore location; **no arbitrary physical-file injection is needed now**. Rust writes a bounded fixed synthetic bootstrap into a new private run dir, then existing PhysicalReadHandler really reads it. Synthetic data/authority/purpose/offline endpoint are installed in trusted Rust composition, not Kotlin. No production database migration/access, network permission or credential. This is a real runtime chain over explicit synthetic inputs; do not call it product business capability.

Candidate caps:1 process-wide occupied native runtime/run,1 Rust worker,1 retained one-shot run per runtime; no queue/retry. Explicit Agent Limits steps2/calls2/context32768/output16384/total65536, plus independent host read admission budget1. Turn1 advertises only the selected installed operation; after its admitted read, turn2 tools empty. Dispatch must also reject a second read even if a provider returns a known operation; do not rely on endpoint goldens or only overall maxcalls. Exactly2 endpoint admissions and1 read are positive completion assertions, not defaults guaranteed on failure. No third provider call. Existing response/payload/envelope and ledger-body<=65536bytes remain unchanged; bootstrap/physical raw<=8192bytes is a NEW guard to implement (current physical reader permits Core's1MiB read and must be tightened in this bounded path), native.db<=65536bytes already exists. Candidate task.db<=128KiB is a NEW stricter encoded-task guard for the new facade/host path, without changing Core's global1MiB primitive. Candidate outbound.db<=512KiB is an outer serialized-file limit only (existing body<=64KiB must remain; escaping can approach384KiB). These pre-read/pre-write caps and valid siblings require implementation/tests, not silent truncation or claims current code already enforces them. Cooperative run deadline5s; endpoints poll bounded chunks; no promise arbitrary filesystem syscall can be forcibly killed on deadline.

Finite retention:MAX_RUN_DIRS8,MAX_OWNED_BYTES8MiB including completed/failed/incomplete dirs, known transaction remnants and locks. Obtain the **same exclusive root lock** while bounded-enumerating, reserving quota and fresh atomic mkdir, across controllers/processes; reserve the maximum per-run transaction high-water budget before any bootstrap/write (proposed1MiB, including simultaneous old/candidate/temp snapshots), then retain ownership until safe cleanup/terminal handoff. If complete bounded layout cannot fit this reservation, refuse before starting, never overcommit by just checking current bytes. In-process atomic slot alone does not enforce cross-process quota. Directory basename is a Rust-generated nonce, never request_id; collision refuses/retries only before any run admission with bounded attempts. Existing dirs/files are never overwritten, reset, deleted or auto-replayed to create capacity. Overflow/unknown names/symlinks/nonregular files/invalid receipts/interrupted run return RecoveryRequired; retained state remains for a separately approved inspection/recovery task. No unlimited scanner/list UI or automatic cleanup. Record exact pending/incomplete marker before execution so process restart cannot mistake unfinished work for fresh authorization. Root inventory bounds are a small adapter precondition, not a general storage framework.

Root is trusted OS bootstrap input, not user text. Preserve UID/0700/0600, symlink ancestor checks, private directory lock, strict loaded snapshot validation, atomic file/parent fsync. An arbitrary caller-supplied path string cannot prove Android app identity by itself; Kotlin is trusted only for platform root acquisition, not authority. Existing check-then-open code is not an openat/O_NOFOLLOW race-proof hostile same-UID sandbox. Make no generalized sandbox claim; a stronger adversarial filesystem model needs separate design. Android-specific persistence behavior remains a device gate.

Controller is Send+Sync and owns only Arc atomic control/short-lock records/join management; it never owns or borrows Rc session across FFI threads. run_once takes a strong controller lease, claims global slot, starts exactly one Rust thread, and joins outside locks. Worker constructs NativeStore/transport/authority/review/handler/State/ModelGateway and runs the same drive, then drops Rc/session/store/transport. Only after **actual worker termination and join** may run_once publish closed cleanup and release process slot. Synchronous run_once is called from existing dedicated Kotlin background admission; no listener/callback executes under native admission locks.

request_cancel only sets a correlated Rust control signal independently of busy request queue/session borrow; Requested means pending, not Cancelled. The same signal/deadline must be checked at RuntimePorts admission, provider poll/endpoint/decoder, before physical handler, after raw preservation/before projection, and final send. Existing AgentControl only reads cancel.request, so integrating signal into host-controlled provider polling is required, or retain an independently written authenticated existing file signal; do not assume atomic flag automatically reaches Core. No second Agent loop. Cancel cannot wait for busy Rc borrow. Before native admission, request_cancel returns NotRunning and DOES NOT mean the Kotlin Accepted work stopped; it never latches authority against a future unrelated request. UI Accepted is distinct from native admission. To stop a not-yet-entered run, close linearizes a sticky no-new-start flag under the same short admission lock; subsequent run_once rejects Closed, while a concurrently already admitted worker receives its signal. UI must retain occupancy until actual call returns, not treat NotRunning as terminal. Close prevents new start and requests cooperative stop; Closed only after join/drop/lock release, otherwise Closing. For active work, handle Drop/cleaner only signals; it must not join/block cleaner thread or release slot. An unopened/never-admitted controller may close immediately after proving no worker/resources exist. Strong run/join/controller ownership outlives loss of FFI/UI handle. Reopen while old worker runs stays Busy. Dismiss/timeout are presentation-only unless explicitly issuing request_cancel. If OS I/O does not return, remain Closing/Busy; no kill-thread/reset or replacement worker. Unknown original receipt never auto-resends on close/restart/new holder.
