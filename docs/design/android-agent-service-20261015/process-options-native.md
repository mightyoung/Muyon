## A / B / C comparison

| | A: UI-process Rust worker | B: ordinary private :agent Service | C: isolatedProcess Service |
|---|---|---|---|
| Objects isolated | No address-space separation between UI and Agent/host; worker serializes ownership only | UI separated from entire Agent/host runtime memory and many native crash/hang effects; inner trusted modules share Service process | Additional OS-restricted process for all code placed there; not automatically per-module isolation |
| Non-Send state | Construct/use/drop Rc only on Rust worker inside UI process | Same worker entirely inside Service process; Binder pool sees only Send/Sync controller+DTO | Same worker rule, plus capability/broker boundaries |
| App-private store | Existing UID/path design potentially reusable after Android validation | Ordinary same-app process can use same app-private store; exclusive root lock must coordinate processes | Cannot assume original app-private root or privileges; current UID/path checks incompatible with simply handing over app's root |
| Lifecycle | UI process death kills runtime too; worker/Drop not guaranteed | Runtime process may fail independently; binding/unbinding and process death require explicit handling; no immortal background guarantee | B lifecycle complications plus restricted resources and broker death |
| Added surface | Small local FFI/controller surface; no native crash containment from UI | Service/AIDL/version/correlation/death/reconnect/lookup surface; Kotlin adapter remains transport only | Restricted data/storage/authority broker or redesigned store; expands trust/IPC architecture |
| Suitability | CANCELLED as first/transitional route; comparison only | REQUIRED direct first slice; no A-first prerequisite | Not a drop-in whole-Agent-with-same-store option; defer unless restricted privilege boundary is an actual requirement |

Platform basis: a colon-prefixed process is app-private; `exported=false` limits external entry; `isolatedProcess=true` has no own permissions and communicates through Service APIs. [Official service manifest](https://developer.android.com/guide/topics/manifest/service-element). Android's app sandbox is UID-based and applies to native code; separating ordinary processes is not creating another application's UID boundary. [AOSP application sandbox](https://source.android.com/docs/security/app-sandbox). **Inference from those sources and source store UID check:** B can preserve app-owned store semantics without a new permission broker; C cannot be assumed to open that same0700 root. Exact API24/OEM UID/path/SELinux/lock behavior still needs platform verification. No proposal should relax store permissions to make C work.

For C, options such as a trusted Rust storage/authority broker or carefully delegated descriptors require a new capability/IPC contract and likely changes to path-based store APIs; a descriptor is not evidence that the unchanged store will work. A broker must remain Rust-owned for business/authority/receipt policy; Kotlin cannot become the substitute authority or a second receipt store. Whole-Agent C and the current one-owner durable filesystem model cannot simply both be asserted without resolving this conflict.

## B can start directly, but requires a genuine remote contract

Service lifecycle callbacks are not a worker. Remote AIDL methods can arrive concurrently from a Binder pool; synchronous calls must not block the UI thread. [Official AIDL guide](https://developer.android.com/develop/background-work/services/aidl). Therefore Service's thin adapter should validate bounded transport fields and invoke one Rust controller; it must not run/move Rc sessions on Binder threads. The Rust worker constructs State/NativeSession/provider/handlers/store, runs the existing drive and drops them locally. Quick cancel/close cannot queue behind run or acquire its busy Rc borrow. AIDL `oneway` means transport submission, not durable native acceptance or terminal acknowledgment.

A direct B first slice needs: explicit non-exported binding, one Service-owned root/runtime gate, bounded versioned request/report/control messages, durable admission correlation before an accepted reply, resource caps, death/connection-state handling and read-only evidence lookup. Service derives platform private root itself; UI sends no arbitrary root/declaration/authority. The PR84 metadata-only diagnostic may remain in the UI process: its fresh Catalog inspection constructs no Agent/NativeSession/store. It need not be moved into Binder merely to land B. Its own diagnostic single-flight is separate from the sole Service-owned Agent gate; it must never construct/run Agent, open Agent store paths, or claim B execution readiness.

Pure bound Services can be destroyed when clients unbind; separate placement is not a promise to survive UI death or background execution. [Official bound-service lifecycle](https://developer.android.com/develop/background-work/services/bound-services). First slice may remain visible/bound and explicitly cease new work when disconnected; no foreground Service, new permission or background execution promise is implied. Parent must select lifetime/retention behavior, not depend on an Activity's onDestroy.

## A → B reuse versus real rework

Reusable unchanged in principle: core drive, registered declarations, host physical handler/args/ref binding, sourcefacts/purpose, raw receipt owner/store validation, projection/history barriers, bounded offline encoder/Decoder/provider. A private Rust control/DTO contract using opaque run IDs, not Arc pointers or UI callbacks, also ports well.

New B work even with reusable Rust: Service manifest/lifecycle, remote generated AIDL/Parcel codec, binding states, caller/correlation validation, remote errors/death, service-incarnation identity, durable request→task/attempt lookup and no replay on rebind. Process globals/Application singleton are not shared across A and B; the execution gate must be server-owned with a cross-process root lock. Thin Kotlin marshalling is platform glue, not business rewrite. A long synchronous FFI function/Arc object designed as a UI contract cannot be passed through Binder; reusing it without adaptation would create another lifecycle model. A-first is cancelled: freeze the data/control protocol directly for B. The reuse analysis above explains why existing Rust stays useful; it is not a proposal to ship A first. No precise schedule is supported by current evidence.

## Concrete B contract candidate for root review (not source implementation)

Only an explicit `exported=false`, `android:process=":agent"` bound Service owns runtime creation. Whole Agent, registered read handler, live authority/purpose/sourcefacts, provider protocol and receipt/store live in Rust inside that Service. UI owns a Binder proxy and presentation state only; Service Kotlin is bounded IPC/JNA/Android glue, never an authority or receipt implementation. Application initialization runs separately in each process, so do not initialize an Agent/gate in the UI process or rely on an Application singleton across processes. One Service-side Rust worker owns all Rc construction/use/drop. Keep visible/bound finite work; no daemon, foreground Service, new permission, model or credential proposal.

Candidate versioned IPC surface (typed records/enums, no pointers/callback business values):

```
submit(ReadIntent { protocol:1, request_id:SafeAsciiId, variant:BuiltinReadVariant })
    -> Queued { service_epoch, request_id } | Busy | Rejected(SafeError)
status(RequestRef { protocol, request_id, expected_service_epoch? })
    -> QueuedVolatile | DurablyAdmitted(RunIdentity) | Running(RunIdentity)
     | Terminal(RunSummary) | Rejected(SafeError) | RecoveryRequired
result(RunRef { protocol, run_id }) -> Pending | Terminal(RunSummary) | RecoveryRequired
cancel(RequestRef) -> Requested | AlreadyTerminal | NotRunning | Rejected(SafeError)
close(ServiceSessionRef) -> Closing | Closed
lookupOriginal(RequestRef) -> Existing(RunSummaryOrPending) | Unresolved | RecoveryRequired
RunIdentity { run_id, task_attempt:Option<TaskAttempt { task_id, attempt_id }>, admitted_service_epoch }
RunSummary { protocol, request_id, identity, observed_service_epoch, build_identity,
 terminal:Completed|Cancelled|Failed|BudgetExhausted|OutcomeUnknown,
 reason:closed safe enum, original_receipt:{opaque_id?, outcome:
 NotStarted|ReceiptUnknown|RunningUnknown|RecordedSuccess|RecordedFailure} }
```

Method-specific state/race rules: submit is valid only in Ready and atomically claims the sole volatile slot before returning Queued; duplicate intent returns DuplicateIntent and never schedules work. During QueuedVolatile, cancel sets that exact request's signal and close seals further admission, without claiming a durable run or cancellation terminal. During durable admission/start, the same controller lock/signal ordering prevents cancel loss; worker checks signal before physical admission. status/result/lookup are read-only and cannot create a task, grant or handler call. A stale expected epoch returns EpochMismatch plus an allowed explicit original-intent lookup path, never implicit re-submit or close of the new epoch. result before terminal returns Pending; it never fabricates a final receipt. close transitions Ready/Queued/Running→Closing; Closed requires actual join/drop and authoritative terminal reconciliation, while process loss remains HostDied/TransportLost. Status of a durably admitted but incompletely indexed/recovered run stays RecoveryRequired/ReceiptUnknown, never disappears into NotStarted.

`ServiceSessionRef` is `{protocol, service_epoch}`; close with a stale epoch returns a safe epoch-mismatch, never closes a new incarnation. `SafeError` is closed: UnsupportedProtocol, InvalidRequestId, EpochMismatch, DuplicateIntent, Busy, Closed, TargetUnavailable, AuthorityDenied, PurposeDenied, ContractRejected, StorageFailure, ProviderFailure, DeadlineExceeded, BudgetExceeded, RecoveryRequired, InternalFailure. No raw Rust/OS exception is marshalled as a public reason. Run terminal reason uses the corresponding safe cause or None/Cancelled/Interrupted; do not derive it solely from existing native_host_refused. A duplicate submit never executes again; caller uses lookupOriginal, not reconnect/resubmit. Unknown run IDs map to Unresolved/RecoveryRequired where evidence could exist, never an inferred NotStarted.

`Queued` acknowledges only bounded volatile server admission, NOT durable NativeAccepted, execution or permission. Worker reserves storage/run identity and fsyncs a request→run admission record **before** publishing DurablyAdmitted/starting the existing chain. NativeAccepted means this run_id admission is durable, not that task/attempt have already been fabricated. task_attempt is absent until actual State::runtime creates both identifiers, then persisted and published as an atomic pair; exactly one missing identifier is invalid. No UI-visible accepted state can be fabricated before this. Cancel of QueuedVolatile sets the independently correlated signal, observed before durable execution; NotRunning is not cancellation proof. This two-stage design avoids filesystem work/long execution in Binder or main-thread callbacks. Poll/result reads small immutable controller snapshots; it does not borrow busy Rc. Startup root inventory/recovery runs before server Ready, not inside an uncontrolled parallel lookup. No client should need a long synchronous Binder call or a result callback to keep business truth.

Safety/limits candidate: protocol1; ID `[A-Za-z0-9_-]{1,64}`; opaque random run_id/epoch fixed bounded forms; four Rust-owned built-in synthetic variants, seed0x7631; no arbitrary path/declaration/policy/provider supplied over Binder. At most one admitted/queued run and one Rust worker per Service; one cross-process root lock prevents overlapping old/new owner. IPC request/control<=4KiB and status/result<=8KiB encoded, fixed small field/list counts; this is an app cap, not Binder delivery guarantee. No raw/modelhistory/projection/answer or counters in shipping Binder results. Real safe projection→second model payload remains inside Rust, verified through off-shipping probes. Existing business/model send UI remains disabled.

Execution caps proposed in previous report remain candidates requiring tests: Agent steps2/calls2 plus native read budget1, turn2tools empty AND dispatch denial of a second read, existing model/envelope/body<=64KiB, new raw bootstrap/read<=8KiB, existing native.db64KiB, new encoded task.db128KiB, outer escaped outbound.db512KiB without relaxing inner ledger body64KiB. Cooperative deadline5s does not promise forced cancellation of arbitrary filesystem calls. Root namespace max8runs/8MiB including temp/lock/source/admission evidence, with upper-bound2MiB peak reservation per run under the **same root lock** as inventory+mkdir; unknown/corrupt/incomplete/overflow refuses rather than deletes/resets/replays. The2MiB peak includes simultaneous old/candidate/temp outbound512KiB×2, task128KiB×2, native64KiB×2, raw/bootstrap, locks/source files AND the new bounded admission/index/run-summary files; it is not2MiB plus an uncounted index. Bound each new admission/index snapshot to64KiB and count both original/candidate versions and replacement remnants; refuse before any write if conservative inventory+reservation cannot fit8MiB. Retained bytes and outstanding reservation are accounted without double-charging committed files but never omitting temporary peaks. These caps are proposed new facade guards, not already enforced by fixed0ab.

Service derives canonical private root from its own Context, installs bounded synthetic physical data and exact host refs in Rust. Do not pass UI root/file data; ordinary same-UID Service matches current UID-owned filesystem model in principle. Durable admission index/run-summary/recovery-readable metadata is NEW adapter work, with one original NativeStore raw receipt owner; no competing business receipt. Need write ordering tests if index and native.db are distinct files; missing/partial index cannot be used to deny known receipt existence or infer no execution. ReceiptUnknown may have opaque_id=None; absence of an ID never implies NotStarted. Reconnection can read old metadata but cannot resume grants, rewrite facts or re-dispatch.

Quick cancel/close update a Rust Arc atomic/controller outside busy run queue/Rc. Host checks it at provider poll, pre/postread, acceptance and finalsend while preserving original file cancellation compatibility; no new Agent loop. Graceful terminal/result is published after worker cleanup/join and durable classification. Service death is a separate fact handled below, never a fake join result. Resource/lifetime/queued-vs-admitted races and process-scoped bootstrap need exact review before writer activation.

### Inner Catalog decision, explicitly still open

Preferred proposal to parent for trusted compiled built-ins: one persistent Catalog inside the :agent Rust worker behind a private bounded ContractTransport, unchanged Linux PluginProcess adapter retained as regression/differential path. This would avoid Android executable spawning, but deliberately removes the old child Catalog address-space boundary; it requires explicit approval and fatal/ordinary reply/close/ticket parity tests. B's whole-Agent↔UI separation remains even with this inner choice. **This report does not count trusted-built-in or outer B authorization as that approval.**

Alternative if the Catalog boundary must remain a real Android process: a second system-managed private contract Service with its own bounded IPC/protocol/lifecycle, host remains in :agent. This is more adapter/death/correlation scope, not a direct use of unchanged Linux pipes/exec. It does not move business handlers out of host. Keeping existing POSIX child untouched as the Android implementation is not currently justified by any exec/packaging evidence. No unsupported exec workaround should be implemented. Parent must choose the inner path explicitly; neither ordinary B nor isolated C answers it automatically.

## Death, receipts, cancellation and no replay

`IBinder.DeathRecipient` reports the hosting process going away, not business outcome. [Official death callback](https://developer.android.com/reference/android/os/IBinder.DeathRecipient). `DeadObjectException` can also represent low-level queue/buffer failures; handle it as transport loss, not proof execution never began. [Official exception semantics](https://developer.android.com/reference/android/os/DeadObjectException). A failed transaction can lose either request or reply and have partial effects; use small messages, not raw/history payloads. [Official TransactionTooLargeException](https://developer.android.com/reference/android/os/TransactionTooLargeException).

Engineering consequence: persist a bounded trusted request ID→run_id admission record before reporting NativeAccepted and before handler admission; after transport loss, lookup that **same original intent**, not resend run_once. Current NativeStore does not supply this cross-Binder admission index: it is new bounded adapter work, not existing proof. The durable index first binds request_id→run_id; optional task/attempt are populated only as a real paired State identity, not invented as acceptance metadata. Unknown lookup, missing/corrupt/unreadable record or unobserved acceptance cannot independently prove zero execution. Reconnection only restores a channel; ServiceConnection may reconnect while the binding remains active. [Official ServiceConnection](https://developer.android.com/reference/android/content/ServiceConnection). Never replay a run from onServiceConnected/onStartCommand or a UI retry loop.

Required outcome precedence: durable running/uncommitted receipt→OutcomeUnknown, including cancel/close overlap; raw success→RecordedSuccess even if overall run interrupted; complete receipt is past evidence, never fresh permission. NotStarted requires affirmative trusted evidence that handler admission never occurred; missing receipt ID, pre-begin missing file, arbitrary notFound, a partial index, or an unreadable receipt are not that evidence. Use ReceiptUnknown with optional opaque_id when certainty is absent. A late real receipt must remain evidence even if presentation epoch changed. Preserve existing journal/sourcefacts and do not grant after restart. Process death does not run a reliable Rust Drop/join/onDestroy path; persist-before-read and immutable evidence are necessary. Android can kill processes and lifecycle teardown is not guaranteed. [Official process lifecycle](https://developer.android.com/guide/components/activities/process-lifecycle).

Graceful Closed means worker terminated, Rc/store/transport dropped and joined in its live host process. Binder death is a distinct TransportLost/HostDied fact, not a graceful Closed or Cancelled acknowledgment; old OS process no longer existing does not establish final business outcome. On reconnect, reacquire exclusive root lock and read authoritative evidence before admitting unrelated work; do not erase running receipt, reset namespace or automatically resend. A process-wide atomic slot alone is insufficient across Service restarts/multiple controllers; retain bounded root inventory/reservation under file lock.
