# Android Rust Agent process options — independent security comparison

2026-10-15. Read-only: official Android documentation consulted today and fixed repository `0ab2c4f667681b9aacb017f8cd2eea6f576cf78e`. No implementation, tests, build, model/device access or installation. **Latest explicit user direction rejects A as a first slice or transition and requires B, a system-managed independent service containing the whole Rust Agent.** Trusted built-ins are accepted. The earlier in-process Catalog feasibility report identified a reusable internal seam; it did not approve an Android UI-process Agent runtime.

**Independent assessment supports the now-required B**, with its bounded Binder/lifecycle contract still to review. It gives the whole execution runtime a separate failure domain while preserving most existing Rust composition. A is retained below only as a rejected comparison: it shares the UI process's native crash/hang fate. C offers a distinct permission boundary but requires a larger broker/capability design. This is a source-backed assessment, not a claim of complete sandboxing or authorization to implement before fixed-contract review and root activation.

| Option | Isolation object | Security and recovery limit | Reuse |
| --- | --- | --- | --- |
| A: Rust worker in UI process | Separate thread only | Shared address space, UID and process failure; no safe thread-kill equivalent | Existing Rust chain can remain together; least platform plumbing |
| B: entire Rust Agent in `:agent` Service, Binder control | Separate process for driver, native host, handlers, Catalog, model gateway and receipt store | Crash/termination boundary from UI, **same application permissions/UID**; no sibling-data sandbox | Existing chain remains together; Binder is outer command/status/control boundary |
| C: entire Agent in `isolatedProcess` | Isolated process/UID, no permissions of its own | Access restored by supplied data/FDs/brokers must be constrained; not automatically a complete sandbox | Pure Agent/Catalog logic reusable, privileged file/model/receipt operations need redesign |

Android documents that `android:process=":name"` creates an application-private process and that `isolatedProcess=true` creates a special process with no permissions of its own. Set a private service's exported status explicitly; process naming alone is not IPC access control. [Service manifest](https://developer.android.com/guide/topics/manifest/service-element). Android's application sandbox is based on app UID and also covers native code; a second ordinary process of that app does not acquire a new app permission boundary. Thus B cannot be advertised as preventing its native code from accessing same-UID app files or app-available credentials/capabilities. [Application Sandbox](https://source.android.com/docs/security/app-sandbox). Android separately exposes isolated-UID/process identification; do not confuse that with merely using a colon process name. [Process reference](https://developer.android.com/reference/android/os/Process#isIsolated()).

## Isolate the whole execution runtime, not just Catalog

Fixed `experiments/redesign/plugin-contract-lab/core/src/lib.rs:13–17,124–153` shows Catalog owns metadata/tickets, not physical reads or receipts. Actual reads occur in `rust-agent-host-lab/core/src/lib.rs:387–435` and `src/read_registry.rs:93–118`; actual outgoing bytes pass `src/model_gateway.rs:43–65`; NativeStore owns original raw receipts and facts (`src/store.rs:213–289`). All paths here are under `experiments/redesign/` at the fixed SHA.

Putting only Catalog in a service leaves the physical handler, model adapter and persistence code in the UI process. It also does not make a host-supplied authority object authentic. For B, keep the whole Rust composition in the service: one persistent in-process Catalog plus existing `NativeSession`, `RuntimePorts`, handlers, policy/review, store and `Agent::run_with_runtime_ports` → `drive` (`core-agent-lab/core/src/agent.rs:205–243`). Retain the existing Linux child transport as a separately tested backend. Neither option needs an extra Agent loop, registry or receipt ledger.

Outer and inner boundaries are separate decisions. The user's clarified requirement is the **whole-Agent service process** boundary, not merely the old Catalog child. It does not by itself require a second Android child inside that service. For trusted built-ins, keeping Catalog in the service together with trusted handlers is compatible with that outer boundary, but the revised contract must say so explicitly; no silent fallback or UI-process execution is permitted. Preserve the existing Linux child backend and its claims separately. No evidence here supports inventing an additional Android child requirement or bypassing the required service with A.

## B: recommended bounded shape, with honest limits

The service still needs a dedicated worker owning `Rc<RefCell<NativeSession>>` (`rust-agent-host-lab/core/src/lib.rs:116`), rather than executing native work on service main/Binder threads or declaring non-Send values thread-safe. Remote Binder calls can arrive concurrently on Binder pool threads; marshal execution into the single owner and keep cancel/control independent of its occupied work queue. [Processes and threads](https://developer.android.com/guide/components/processes-and-threads). A local-Binder cast is only appropriate within one process; cross-process calls need a marshalled interface. Messenger serializes requests, so simply putting cancellation behind long work in that queue does not solve cancellation. [Bound services](https://developer.android.com/develop/background-work/services/bound-services).

A private service process allows the app to handle that process's loss separately and to design a process-level stop/restart policy; it does not guarantee UI survival under every system resource failure or instant, successful kill. Process termination APIs retain kernel restrictions. [Process.killProcess](https://developer.android.com/reference/android/os/Process#killProcess(int)). Admission remains host policy: Binder connectivity, same UID, a registered tool or a UI-provided Boolean is not a live read grant. Keep selected typed refs, current authority, final payload review and original receipt ownership in Rust.

Use bounded task/control/status messages with task/attempt/generation identity and opaque receipt outcome. Do not move raw results, model context, arbitrary paths, authority JSON or plugin tickets into a generic Binder API. Closing a UI screen means detaching presentation unless the explicit task policy requests cancellation. Last-unbind behavior and activity-independent lifetime must be specified; bound-only services normally disappear when their last client unbinds. [Bound service lifecycle](https://developer.android.com/develop/background-work/services/bound-services#Lifecycle). Background/foreground execution policy remains a concrete Android design decision, not something the process attribute supplies.

## Binder loss does not prove cancellation or absence of a read

Official `DeadObjectException` documentation includes both process death and low-level Binder errors, including a full one-way queue or Binder buffer; these cannot reliably be distinguished at runtime and require resetting the connection. [DeadObjectException](https://developer.android.com/reference/android/os/DeadObjectException).

Our required inference is therefore: lost Binder reply/timeout is **outcome unknown**, not “not executed,” “rolled back,” or terminal canceled. The handler may have run and its original receipt may already be durable. Even confirmed process death says nothing about completed reads before death. Reconnect/reconcile task/attempt against the original store; do not automatically resend. A durable running/raw-null receipt must remain unresolved rather than being relabeled by generic failure text. Preserve current begin-before-handler and raw-before-projection ordering (`rust-agent-host-lab/core/src/lib.rs:387–435`) and strict `NativeStore::open` (`src/store.rs:188–204`). Current code has no complete restored live-session protocol; this remains required work for A or B.

## C: isolation gains require a new authority broker

Under C, an app-private pathname is not itself delegated access. Existing code requires owner `geteuid()`,0700 private directories, private file operations and locks (`core-agent-lab/core/src/store.rs:5–40`); PhysicalReadHandler and NativeStore depend on those APIs. An isolated worker cannot simply reuse the normal app's private-directory assumptions. Do not relax ownership checks or make data world-readable to make it work; Android explicitly discourages that pattern. [Application Sandbox file sharing](https://source.android.com/docs/security/app-sandbox#guidelines-for-sharing-files).

ParcelFileDescriptor can pass actual descriptor access with explicit read/write modes, and dup/detach have ownership semantics. [ParcelFileDescriptor](https://developer.android.com/reference/android/os/ParcelFileDescriptor). Security inference: handing C a broad writable directory/database descriptor, a socket, credentials or a generic “open arbitrary path / send arbitrary payload” broker restores substantial authority despite its isolated UID. Closing one duplicated FD is not revocation of all delegated copies, and receipt already read into memory cannot be retracted. Grant narrow selected-record/data access only; if true revocation before each operation is needed, mediate that operation through a live checked broker rather than relying on an irrevocable already-delivered snapshot.

The trusted broker would need to bind caller/session/attempt, selected object+revision, allowed operation, purpose, expiry/revocation and original receipt identity; validate each request rather than trust worker-provided authority or a declaration. It must not become a confused deputy. For an untrusted worker, checks inside that worker cannot protect the broker. Durable raw receipt persistence, actual-value classification and final model-byte send admission must live in the authority-owning side or be verified there. Preserve exactly one original receipt owner and no alternate sender. Current `ReadHandler`, `AuthoritySource`, `PurposeReview` and ModelGateway seams are useful starting points, but their synchronous/local ownership cannot be replaced with unrestricted callbacks without a new protocol and failure analysis.

For trusted built-ins, that is materially larger than B and presently unnecessary to meet process-failure isolation. C becomes justified if the requirement changes to executing untrusted plugin/native code with reduced file/network/credential rights. Even then FD/Binder capabilities, platform policy and the broker's attack surface prevent a blanket “strong sandbox complete” claim.

## Before implementation

B is now mandatory; do not propose A as a transitional delivery. Original native/UI owners are drafting service epoch, admission/query/cancel/close, death-unknown, read-only outcome lookup, no-replay and service-owned persistence. Freeze and independently review that concrete protocol before root activation, with independent cancellation and durable unknown outcomes preserved. No added foreground-service/background-daemon or model/network permission is implied. Effective acceptance must separately test service loss after receipt begin/after read/before reply, Binder failure without assuming process death, stale callbacks/rebind, busy/cancel/close and lock ownership after actual process termination. No such tests were run in this comparison. The current native model gateway remains offline-only; any expanded provider authorization remains separate.
