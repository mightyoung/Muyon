## Deterministic death / receipt / unknown test design (proposed, NOT_RUN)

Use a test controller outside the killed process, a fresh private root and authenticated test-only phase barriers. Wait for exact run/attempt/service-generation and durable phase acknowledgement; then kill the **actual service process**, not merely throw a fake RemoteException. Confirm its death before rebind, UI survival and new service generation. Never rely on sleeps, forced whole-app stop, callback order or `onDestroy` being called. OS-death testing is separate from cooperative cancel/close.

| Frozen barrier / control | Required durable and client oracle after reconnect |
|---|---|
| Healthy sibling with no kill | Real one read, one original completed raw receipt, two admitted payloads, final task outcome and same result on read-only status query; no new execution |
| Before native admission / after explicit durable rejection | Zero handler/receipt/model admission for the rejected operation; a valid fresh sibling proves setup and authority work. Lost Binder reply alone does not prove this phase |
| After durable running receipt, before physical read | Preserve original running/unknown receipt and task evidence, no automatic resend, no fabricated cancelled/completed receipt. A status-only reconnect must not create a new attempt; independent fixture observation confirms this controlled run read0 |
| After physical-read barrier, before raw durable finish | One actual read observed by test oracle, original durable receipt unresolved/unknown, no projection/final send or automatic retry; process loss cannot manufacture the raw result |
| After raw receipt durably finished, before result/terminal delivery | Exact raw receipt/outcome survives, handler remains1, safe task terminal may still be unresolved. Loss of UI reply cannot erase receipt, infer task success, or trigger another read |
| After durable task terminal, before Binder reply/callback | Reconnect/status reports the existing correlated terminal record, not a second run. Suppress the original delivery deliberately to exercise reply-loss sibling without killing |

These are proposed observability/barrier requirements, not existing API guarantees. If the current state writer cannot distinguish a checkpoint, add a reviewed test-first durable transition rather than overstate the oracle. Handler read evidence belongs in private test fixture/oracle; do not fabricate production counters. Real restart must not reconstruct live authority/grants from retained evidence or auto-resume unknown work.

Binder death detects loss of its hosting process, not business completion. [IBinder death](https://developer.android.com/reference/android/os/IBinder.DeathRecipient). Connection loss may reconnect; dead binding requires explicit cleanup/rebind and is distinct. API24 must not depend on the API26 `onBindingDied` callback. [ServiceConnection](https://developer.android.com/reference/android/content/ServiceConnection). Binder transport can fail before request or after service execution while returning the response; treat ambiguous submission as unknown pending durable reconciliation, never safe automatic retry. Small app-level limits are required; the documented shared transaction buffer is not an application budget. [TransactionTooLargeException](https://developer.android.com/reference/android/os/TransactionTooLargeException).

Also freeze Android negatives: duplicate/stale run token; simultaneous start from two Binder threads/clients; overflow while active without queue growth; slow/dead callback without worker/admission lock retention; cancel while provider/handler barrier blocks; UI death/unbind versus service death as separate cases; background transition and service restart with retained locks/unknown evidence.
